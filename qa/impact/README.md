# Анализ влияния изменений Dark Factory v1

Планировщик связывает объявленное изменение с компонентами, требованиями и нужными проверками. Он показывает основание выбора и сохраняет план для дальнейшего выполнения. Это этап 2 развития Dark Factory. Команды установки и рабочий пример находятся в [инструкции оператора, раздел 10.7](../../docs/operator/service-and-lab.md#change-impact).

Инструмент `qa/tools/plan_changes.py` не читает Git diff, не выполняет тесты и не запускает модели. Полная регрессия остаётся обязательной. Список приоритетных селекторов помогает начать разбор с затронутых требований, но не разрешает сократить приёмочные проверки.

## Как определяется влияние

[map-v1.json](map-v1.json) описывает 20 компонентов. У каждого есть пути, зависимости `depends_on`, требования, профили проверок и объяснение. Изменение сначала сопоставляется с точным путём или префиксом каталога, заканчивающимся `/`. Совпадения суммируются; сравнение путей не зависит от регистра. Затем влияние распространяется от изменённого компонента к его потребителям по обратным связям `depends_on`. Циклы и неизвестные ссылки отклоняются.

Например, активный системный промпт находится в `src/runtime/transport.py`. Его изменение затрагивает протокол LLM, генерацию и последующих потребителей результата. Изменение только UI не требует новой модельной оценки по этой карте; полная детерминированная регрессия всё равно сохраняется. Общий HTTP-клиент `src/workflow/remote.py` относится также к Kafka: его использует обработчик для устойчивого повторения запросов после потери подтверждения. Отдельно учитываются файлы тестов и источников ожиданий, прямо перечисленные в каталоге требований.

Карта составлена вручную и закрепляет канонический хэш каталога требований в `catalog_sha256`. Изменение требований требует пересмотра связей; простая замена хэша не подтверждает их правильность. Это не автоматически построенный граф импортов и не доказательство полноты семантических зависимостей.

## Входной контракт

Для одного или нескольких путей повторяйте `--changed`. Для смены модели вне файлов используйте `--model-changed llm` или `--model-changed embedding`. Состояние Ollama и модельные файлы сами по себе не обнаруживаются.

`--changes-file` принимает строгий JSON из файла внутри проекта:

```json
{
  "schema_version": "1.0",
  "changes": [
    {"status": "M", "path": "src/runtime/generation.py"},
    {"status": "R", "previous_path": "src/runtime/transport.py", "path": "src/new_domain/transport.py"}
  ],
  "model_changes": ["llm"]
}
```

`A`, `M` и `D` означают добавление, изменение и удаление; у них только `status` и `path`. Для `R` обязательны оба пути. Переименование рассматривается как объединение влияния старого и нового пути. Для сопоставления с картой существование файлов не требуется; отдельно валидатор читает тесты и основания, на которые ссылается каталог требований. Если связанный файл или объявление теста удалены, план сохраняется как `INCOMPLETE` с полным резервным набором и кодом причины в `catalog_validation_error`. Изменение закреплённой политики остаётся `ERROR`, пока её связь с каталогом не пересмотрена. Windows-разделители нормализуются. Абсолютные пути, выход за корень, неоднозначные дубликаты, неизвестные поля и повторённые JSON-ключи отклоняются.

Пример выше намеренно содержит неизвестный новый путь: ожидается `planning_status=INCOMPLETE`. План сохраняет старые связи, включает все требования и все профили как консервативный резерв и перечисляет неизвестный путь. Эти действия ничего не перемещают и не переименовывают в проекте.

## Результат и смысл статусов

Результаты создаются только в новом каталоге `var/qa/impact/<имя>`. Сохраняются `changes.json`, `catalog.json`, `map.json`, `catalog-validation.json`, `result.json` и читаемый `plan.md`. При ошибке набор может быть неполным; `started.json` без итогового результата означает прерванную работу.

| Поле | Значение |
| --- | --- |
| `planning_status=READY`, код 0 | Для объявленных входов составлен план по известным связям |
| `planning_status=INCOMPLETE`, код 2 | Есть неизвестные пути или исчезли ссылки каталога; выбран полный резервный набор |
| `planning_status=ERROR`, код 2 | Не удалось проверить входы, карту или сохранить результат |
| `input_completeness=NOT_VERIFIED` | Полнота объявленного списка изменений не доказана |
| `execution_status=NOT_RUN` | Ни одна проверка этим инструментом не выполнялась |
| `requirements_status=INCOMPLETE`, `product_acceptance=INCOMPLETE` | План не подтверждает качество или приёмку |
| `candidate_admission=NOT_EVALUATED` | Решение о допуске кандидата не принималось |

`path_impacts` раскрывает прямые совпадения, использованные шаблоны путей (`matched_patterns`) и по одной объясняющей цепочке до каждого достижимого компонента. `requirements[].reasons` объясняет связь входа с требованием; `selected_test_selectors` перечисляет приоритетные тесты. `requirements_without_declared_impact` означает только отсутствие связи в этом плане, а не доказанное отсутствие влияния. Хэши фиксируют содержимое входной декларации, карты и каталога; они не удостоверяют состояние всех исходников, окружения или модели.

## Профили проверок

| Профили | Как выполнить |
| --- | --- |
| `full_regression` | Обязательная общая регрессия и сверка контрактов: раздел 10.1 основной инструкции |
| `requirements` | Запуск всего каталога требований по разделу 10.6; выбор селекторов в плане не меняет эту команду |
| `ui_cli`, `browser` | AppTest/CLI из раздела 10.1 и браузерный smoke из 10.2 |
| `retrieval`, `llm`, `judge` | Отдельные реальные измерения по разделу 10.3 с подготовленными моделями |
| `live_integration` | Проверка живой SQL/API/Kafka → AML → UI цепочки по разделу 7 |
| `documentation`, `mapping_review` | Проверка инструкций и обоснованности связей; эти записи не являются выполненной автоматической проверкой |

Все профили в плане имеют `status=NOT_RUN`. У некоторых есть `entrypoint`, но это указатель на инструмент, а не готовая команда со всеми параметрами. Отсутствующая модель, зависимость или человеческая оценка остаётся неподтверждённой. Человеческая часть проверки карты и предметных ожиданий отложена до соответствующего этапа плана.

Валидатор не разрешает удалить обязательный профиль `llm` из модельного компонента `model_llm` или `retrieval` из `model_embedding`. Явная смена модели должна сохранять требование живого измерения даже после редактирования остальных зависимостей.

Тесты планировщика входят в существующий набор `tests/dark_factory`. Этап 3 добавляет [общий запуск детерминированных проверок и привязку свидетельств к версии](../execution/README.md). Результаты планирования остаются локальными; исходники карты, планировщика и тестов входят в QA-блок публикации.
