# Исполняемые требования Dark Factory v1

Каталог связывает требование с риском, основанием ожидания и существующими программными проверками. Инструмент отдельно проверяет описание и выполняет выбранные тесты, после чего перечисляет подтверждённые и неподтверждённые требования. Это этап 1 нового плана развития Dark Factory. В этапе 2 добавлен [анализ влияния изменений](../impact/README.md): он использует этот каталог для обоснования плана проверок. Полная привязка свидетельств к версии остаётся следующим этапом.

Порядок установки окружения, команды запуска, результаты и диагностика собраны в [инструкции оператора, раздел 10.6](../../docs/operator/service-and-lab.md#executable-requirements). Файл запуска — `qa/tools/check_requirements.py`; каталог — [catalog-v1.json](catalog-v1.json).

## Что описано

| Требование | Проверяемое поведение |
| --- | --- |
| DFR-001 | Готовность обработчика и допуск задания |
| DFR-002 | Сохранение отмены/дедлайна и остановка обработчика |
| DFR-003 | Точная связь факта с неизменённым источником |
| DFR-004 | Полный каталог разрешённых фактов и точные суммы |
| DFR-005 | Однозначная редакция правила; ранжирование не определяет применимость |
| DFR-006 | Авторизованное решение сохраняется с серверной атрибуцией |
| DFR-007 | Экспорт относится к конкретной одобренной версии |
| DFR-008 | Входящее Kafka-событие сохраняется до подтверждения offset |
| DFR-009 | Повтор события идемпотентен; замена содержимого блокируется |
| DFR-010 | Недоверенный текст отделён от команды модели |
| DFR-011 | Judge не подменяет программные проверки и человеческую оценку |
| DFR-012 | Ошибки и неполные измерения не превращаются в допуск кандидата |

В версии 1.0 — 12 требований, 24 сценария и 41 уникальный селектор тестов. Количество собранных параметрических случаев определяется текущим кодом тестов. В каждой записи есть собственные `scope` и `limitations`: например, проверка Kafka с подменённым транспортом не доказывает работоспособность живого брокера.

## Контракт каталога

Корневые поля: `schema_version`, `catalog_id`, `version`, `title`, `scope`, `policy`, `requirements`. Поддерживается версия `1.0`, идентификатор `dark-factory-requirements-v1`. Неизвестные поля, повторённые JSON-ключи и нечисловые значения JSON вроде `NaN` отклоняются.

| Поля требования | Назначение |
| --- | --- |
| `id`, `version`, `title`, `statement` | Устойчивый идентификатор, версия и проверяемое утверждение |
| `risk`, `priority`, `owner` | Риск, приоритет P0/P1 и вид ответственной проверки; `owner` не является подписью эксперта |
| `scope`, `preconditions` | Граница и необходимые условия проверки |
| `allowed_outcomes` | Явный перечень допустимых исходов |
| `expectation_source.path`, `expectation_source.reference` | Файл и указание основания ожидаемого поведения |
| `limitations` | Что этими проверками не подтверждается |
| `scenarios` | Как минимум один положительный и один отрицательный сценарий |

Сценарий содержит `id`, `kind`, `given`, `action`, `expected_outcome`, `test_selectors`. Исход должен присутствовать в `allowed_outcomes`. Селектор имеет вид `tests/.../test_file.py::test_name` или `tests/.../test_file.py::ClassName::test_name`. Ссылки проверяются по AST без импорта тестового модуля и должны находиться в настроенных `testpaths` проекта. Один селектор нельзя использовать как обе стороны одного требования. Отрицательный сценарий означает проверку правильного отказа; ожидается успешное выполнение его теста.

`policy.canonical_sha256` закрепляет содержимое `qa/strategy/quality-policy.json` после строгого разбора JSON и канонической сериализации. Поэтому переносы строк CRLF/LF, отступы и порядок ключей сами по себе не требуют смены каталога. Изменение значения политики требует осознанного пересмотра требований; несовпадение не следует устранять механическим обновлением хэша. `source_hashes` текущего прогона отдельно фиксируют реальные байты выбранных файлов.

## Выполнение и доказательства

`validate` проверяет форму, идентичность политики, файлы и объявления тестов. Успех этой команды не запускает тесты: `execution_status=NOT_RUN`, `requirements_status=INCOMPLETE`.

`run` выполняет только уникальные селекторы из проверенного каталога. Внешние `PYTEST_ADDOPTS`/`PYTEST_PLUGINS` очищаются на время вызова, автоматическая загрузка плагинов отключается, ini `addopts` переопределяется. Инструмент наблюдает коллекцию и фазы `setup/call/teardown` собственного запуска pytest. Все собранные параметры должны иметь полный успешный цикл; пропуск, xfail/xpass, исключение из коллекции и незавершённые фазы не дают `PASS`. Зафиксированная неудача сохраняется, даже если далее наблюдается успешный вызов.

Перед запуском сверяется связь статической проверки с текущими выбранными исходниками, после запуска — их неизменность. Инструмент создаёт новый каталог `var/qa/requirements/<имя>` и не читает внешний JUnit как основание для принятия результата. Копия каталога, наблюдения, JUnit, лог и сводка относятся к этому запуску. Исторические результаты не перезаписываются; при принудительном завершении отсутствие итогового `result.json` означает отсутствие завершённого отчёта.

| Результат | Область вывода |
| --- | --- |
| `requirements_status=PASS` | Все связанные механические проверки прошли в текущей собранной коллекции |
| `requirements_status=FAIL` | Наблюдалось падение связанной проверки |
| `requirements_status=INCOMPLETE` | Полного подтверждения нет |
| `product_acceptance=INCOMPLETE` | Продуктовая приёмка этим инструментом не выполняется |
| `candidate_admission=NOT_EVALUATED` | Разрешение на выпуск/применение кандидата не выдаётся |
| `human_calibration=NOT_MEASURED` | Независимые человеческие оценки не собирались |
| `historical_judge=NOT_REASSESSED` | Исторический результат Judge не изменялся |

Отчёт не является полным паспортом исполняемого кода, всех зависимостей, модели и окружения. Он не устанавливает независимый ожидаемый размер параметрической коллекции, не подтверждает скрытый holdout, качество настоящей LLM, удобство UI или банковскую приёмку. Ограничения каждого требования остаются частью результата.

## Как расширять

Сначала сформулируйте риск и допустимые исходы на основании политики/спецификации. Найдите или добавьте содержательные проверки разрешённого и запрещённого поведения, обозначьте реальные и подменённые зависимости. Затем добавьте запись каталога, выполните `validate`, `run` и общую регрессию. Проверяйте `unconfirmed_requirements`, а не только код завершения команды. Изменение значения политики, семантики требования или версии схемы требует согласованного пересмотра описания, валидатора и тестов.

Тесты каталога и запуска расположены в `tests/dark_factory` и входят в существующую детерминированную регрессию. Отдельного задания CI, публикующего отчёт требований, на этом этапе нет. Исходники и каталог входят в QA-блок публикации; результаты из `var/` остаются локальными.
