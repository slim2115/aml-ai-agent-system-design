# Поиск и отсутствие релевантного источника — учебные проверки

Новый открытый каталог `development_cases()` содержит две стороны одной границы редакций и один нерелевантный запрос. Это **две темы**, а не три независимых кейса, не экспертная AML-разметка и не скрытый holdout. Пара ожидаемых редакций и цитат вычисляется из вручную заданных синтетических строк отдельно от кода продукта. Корпус предназначен для проверки оценщика, а не оценки качества модели.

`assessment.assess_case(case, raw, selected)` применяет существующую проверку ранжирования `qa.retrieval_checks.evaluate_ranking`. `raw` — фактически полученные кандидаты поиска; `selected` — отдельно наблюдаемый результат последующего решения/фильтрации. `selected=None` означает, что решение не наблюдалось, а `selected=[]` — действительно наблюдаемый отказ. Отбор должен состоять только из исходных кандидатов с полной идентичностью цитаты. На отрицательном запросе выбранный кандидат — ложное принятие; на положительном пустой отбор — ложный отказ. Полнота и посторонние выборы считаются отдельно. Для отсутствующей релевантности метрики ранжирования остаются `null`.

`assess_run` сохраняет числители и знаменатели отдельно для положительных и отрицательных случаев, не считает отсутствие наблюдения успехом и не присваивает экспертную приёмку. `FAIL` имеет приоритет перед `INCOMPLETE` и не маскируется отсутствующими наблюдениями. Ошибочные/подменённые данные вызывают явную ошибку. В тестах используется настоящий `RuleIndex` с тестовым tokenizer и embedding: это проверка кода и измерительного адаптера, **не** испытание настоящего поиска или модели.

Сервис использует собственную политику применимости правил. Её наблюдаемые решения проверяются отдельным измерителем `qa/dark_downstream/live.py`.

### Расширенное упражнение с локальной MiniLM

`live_matrix.py` использует фиксированные запросы рабочего `RuleIndex` по темам дробления, суммы, KYC, риска юрисдикции и отчётности. `matrix_cases.py` задаёт синтетические тексты, сроки действия и ожидаемые полные цитаты. Набор содержит 10 положительных и 7 отрицательных наблюдений. Из них пять отрицательных образованы удалением источника нужной темы. Остальные проверяют запрос о частоте операций и дату без активных документов.

Ранжирование измеряется на CPU с проверенной локальной моделью. Четыре учебных варианта выбора проигрываются на одних и тех же кандидатах. Файл каждого сценария сохраняет первую выдачу. Сводка разделяет завершённость измерения, ошибки каждого варианта и статус экспертной приёмки. Порядок запуска, повторного расчёта и чтения результатов приведён в [инструкции оператора](../../docs/operator/dark-factory-qa-quickstart.md#как-сравнить-пороги-поиска).
