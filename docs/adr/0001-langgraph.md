# ADR-0001: Оркестрация агента на LangGraph

## Статус
Superseded — историческое решение исходного PoC, заменено в rebuild.

## Актуальная реализация · 6 ноября 2026

Текущий путь `src/agent/graph.py` предоставляет совместимый фасад `src.runtime.service.AMLAgent`. Вычислительное ядро находится в `src/runtime`, сохраняемый процесс — в `src/workflow`. Контроллер управляет отдельным процессом, сроком выполнения, отменой и SQLite-хранилищем. В интегрированном режиме контроллером владеет API. Свободный цикл ReAct и LangGraph не описывают действующий пользовательский маршрут.

Причина пересмотра — необходимость явно ограничивать генерацию, сохранять задания и решения, проверять контракты и управлять зависшей обработкой. Цена решения — собственный код управления состоянием и обязанность проверять его переходы. Возможности установленной библиотеки не считаются возможностями сервиса.

Ниже сохранено исходное обоснование июля 2026 года для сравнения архитектурных решений. Его формулировки «используется» относятся к PoC. Текущий процесс описан в [workflow-runtime](../rebuild/workflow-runtime.md).

## Дата
Июль 2026 г.

## Контекст
Агент реализует многошаговый цикл расследования: приём инцидента → агрегация данных (SQL) →
проверка полноты → RAG-поиск правил → генерация черновика → guardrail-проверки → HITL → экспорт.
Процесс содержит ветвления (явный отказ при недостатке данных, корректировка оператором) и
повторяющиеся итерации (цикл ReAct: Reason → Act → Observe).

Требуется механизм оркестрации, который обеспечивает:
* явное управление состоянием агента между шагами;
* детерминированные ветвления и циклы (контроль числа итераций ReAct);
* наблюдаемость (трассировка шагов для audit trail, NFR-11);
* расширяемость без перехода к multi-agent (multi-agent — в Out-of-Scope, BRS раздел 4.2).

## Решение
Использовать **LangGraph** (граф состояний) как основу оркестрации агента.
Каждый шаг процесса (валидация, SQL-запрос, RAG-поиск, генерация, guardrail) моделируется
как узел графа; переходы между узлами — как рёбра с условиями.

## Рассматриваемые альтернативы
* **Чистый LangChain (LCEL-цепочки):** отвергнуто. Линейные цепочки плохо подходят для
  циклов ReAct и условных ветвлений; управление состоянием и повторными попытками становится
  неструктурированным.
* **Самописный цикл оркестрации:** отвергнуто. Требует ручной реализации управления состоянием,
  трассировки и контроля циклов; выше риск ошибок и ниже воспроизводимость.
* **Multi-agent фреймворки (CrewAI / AutoGen):** отвергнуто. Избыточны для одного
  хорошо специфицированного агента; прямо исключены Out-of-Scope (BRS раздел 4.2) как scope-риск.

## Последствия
* **Положительные:** явная и аудируемая структура процесса; контролируемые ветвления
  (отказ, HITL-корректировка); ограниченное число итераций ReAct; лёгкая трассировка шагов.
* **Отрицательные:** зависимость от фреймворка и его версионирования; кривая обучения
  графовой модели состояний.
* **Риски:** изменение API LangGraph потребует миграции; митигируется фиксацией версии
  в зависимостях и инкапсуляцией узлов.

## Связи
* SRS: SR-01…SR-22 (узлы графа реализуют системные требования).
* UML Sequence-диаграмма цикла ReAct (docs/diagrams/sequence-react-loop.puml).
* BRS раздел 4.2 (Out-of-Scope: multi-agent).

### Решение по форме использования LangGraph

Используется LangGraph как **встраиваемая Python-библиотека** (`pip install langgraph`),
выполняемая в процессе приложения. LangGraph Platform/Server (отдельный сервис оркестрации)
**не применяется**, так как:
* агент функционирует в режиме read-only (BR-07);
* HITL-согласование и автоэкспорт вынесены вне агента (Фаза 6-7);
* требования персистентности состояния, стриминга и горизонтального
  масштабирования оркестрации в PoC отсутствуют.

Переход на LangGraph Platform/Server рассматривается как опция производственного
внедрения при появлении требований длительных HITL-циклов и масштабирования
(зафиксировать в Open Items SRS).
