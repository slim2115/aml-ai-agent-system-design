# Модель данных и словарь данных (Data Model & Data Dictionary)

**Версия:** v0.1 (Final)
**PoC: AML / Anti-Fraud Copilot**
**Базовые документы:** BRS v0.4 (Final), SRS v0.2 (Final)

---

## 1. Назначение документа
Документ описывает логическую модель данных PoC-контура AML / Anti-Fraud Copilot: сущности, их атрибуты, связи, а также формат базы знаний комплаенса для RAG-поиска. Документ закрывает следующие открытые вопросы SRS:

- **SRS Open Item №1** — состав полей профиля клиента (раздел 3.1).
- **SRS Open Item №4** — формат базы знаний для RAG-чанкинга и идентификаторы пунктов (раздел 4).
- **SR-14** — детализация структуры `evidence_ref` (`tx_id + field`).

> **Дисклеймер:** Все данные в PoC являются **синтетическими**. Схема учебная и не содержит реальных банковских данных или персональных данных клиентов. Совпадения с реальными лицами и транзакциями случайны.

## 2. Словарь данных (Data Dictionary)

### 2.1 Client (Профиль клиента)
Закрывает SRS Open Item №1 и SR-02 (извлечение профиля).
* client_id — string, PK. Уникальный идентификатор клиента (например, C-00045).
* full_name — string, PII. ФИО клиента. Маскируется в логах и трейсах (NFR-09, 152-ФЗ).
* risk_category — enum {low, medium, high}. Категория риска клиента по результатам KYC.
* kyc_status — enum {verified, pending, expired}. Статус процедуры «Знай своего клиента».
* client_since — date. Дата начала обслуживания.
* inn — string, PII, nullable. ИНН клиента (маскируется).

### 2.2 Card (Банковская карта)
* card_id — string, PK. Уникальный идентификатор карты.
* client_id — string, FK → Client. Владелец карты.
* pan_masked — string. Маскированный номер карты (только последние 4 цифры, например, **** **** **** 7781). Полный PAN не хранится в PoC-контуре.
* card_status — enum {active, blocked, closed}. Статус карты.
* issue_date — date. Дата выпуска карты.

### 2.3 Transaction (Транзакция)
Источник данных для evidence_ref (SR-14). Поле purpose — потенциальный вектор prompt injection (SR-19).
* tx_id — string, PK. Уникальный идентификатор транзакции (например, TX-7781). Используется в evidence_ref.tx_id.
* client_id — string, FK → Client. Клиент-плательщик.
* card_id — string, FK → Card, nullable. Карта, по которой совершена транзакция.
* amount — decimal. Сумма операции. Допустимое значение evidence_ref.field.
* currency — string, ISO 4217. Валюта операции (например, RUB). Допустимое значение evidence_ref.field.
* counterparty — string. Контрагент (получатель/отправитель). Допустимое значение evidence_ref.field.
* purpose — string, injection-risk. Назначение платежа. Обрабатывается как данные, а не инструкция (SR-19). Допустимое значение evidence_ref.field.
* channel — enum {atm, pos, online, transfer}. Канал проведения операции. Допустимое значение evidence_ref.field.
* status — enum {completed, pending, declined}. Статус транзакции. Допустимое значение evidence_ref.field.
* timestamp — datetime. Дата и время операции. Допустимое значение evidence_ref.field.

### 2.4 Case (Кейс / Инцидент)
* case_id — string, PK. Внутренний идентификатор кейса.
* incident_id — string, UNIQUE. Внешний идентификатор инцидента формата INC-\d{6} (SR-01).
* client_id — string, FK → Client. Клиент, по которому открыт кейс.
* alert_type — enum {structuring, high_risk_country, velocity, threshold_breach, kyc_mismatch}. Тип сработавшего алерта.
* status — enum {new, in_progress, pending_manual, closed, escalated}. Статус кейса. pending_manual — результат явного отказа (SR-21).
* created_at — datetime. Время создания кейса.
* closed_at — datetime, nullable. Время закрытия (заполняется при автоэкспорте, SR-22).
* assigned_operator — string, nullable. Оператор, назначенный на кейс.

### 2.5 Rule (База знаний комплаенса)
Источник для source_ref (SR-11) и RAG-поиска (SR-07). Детализация формата — в разделе 4.
* rule_id — string, PK. Идентификатор правила (например, R-115-002).
title — string. Человекочитаемое название правила.
* regulation_ref — string. Ссылка на нормативный акт и пункт (например, 115-ФЗ, ст.6, п.2). Используется в source_ref.
* category — enum {structuring, kyc, threshold, high_risk, reporting}. Категория правила.
* text — text. Полный текст правила/пункта регламента.
* effective_from — date. Дата вступления в силу.
* version — string. Версия документа (для контроля актуальности).

### 2.6 Report (Отчёт / Черновик)
Соответствует JSON Schema из SRS (раздел 8).
* report_id — string, PK. Идентификатор отчёта.
* case_id — string, FK → Case. Связанный кейс.
* status — enum {draft, approved, refusal}. Статус: черновик / одобрен / отказ.
* generated_at — datetime. Время генерации.
* approved_by — string, nullable. Оператор, одобривший отчёт (HITL, BRULE-01).
* confidence — decimal [0..1]. Уверенность модели.
* reasoning_trace — json. Цепочка рассуждений для аудита (NFR-11).

### 2.7 Evidence (Доказательство)
Реализует фактическую обоснованность (grounding, BR-05) и детализирует evidence_ref (SR-14).
* evidence_id — string, PK. Идентификатор записи доказательства.
* report_id — string, FK → Report. Отчёт, к которому относится доказательство.
* tx_id — string, FK → Transaction. Транзакция-первоисточник (evidence_ref.tx_id).
* field — enum {amount, currency, counterparty, purpose, channel, status, timestamp}. Конкретное поле транзакции (evidence_ref.field).
* fact_text — string. Утверждение в отчёте, подтверждённое данным доказательством.
* source_ref — string, nullable. Ссылка на пункт регламента (Rule.regulation_ref), если утверждение имеет нормативное обоснование (BR-04).

## 3. Формат базы знаний для RAG
Закрывает SRS Open Item №4. База знаний комплаенса хранится в виде структурированных документов, разбитых на чанки для семантического поиска (SR-07).

### 3.1 Структура исходного документа регламента
Каждый регламент (например, 115-ФЗ, внутренняя методичка) представлен как набор правил Rule. Документ имеет метаданные:
* document_id — идентификатор документа (например, DOC-115-FZ).
* document_title — название документа.
* regulation_base — нормативная основа.
* version — версия документа.
* effective_from — дата вступления в силу.

### 3.2 Чанкинг (разбиение на фрагменты)
Регламенты разбиваются на чанки по статьям/пунктам. Каждый чанк соответствует одному правилу Rule или логическому пункту. Параметры чанкинга:
* Единица чанкинга: статья/пункт регламента (не произвольные N токенов) — это гарантирует, что source_ref указывает на цельный смысловой блок.
* Перекрытие (overlap): при разбиении длинных статей — 10–15% перекрытия для сохранения контекста.
* Максимальный размер чанка: ~800 токенов (под контекстное окно локальной embedding-модели).

### 3.3 Формат чанка (векторизуемая единица)
{
  "chunk_id": "R-115-002-chunk-001",
  "rule_id": "R-115-002",
  "regulation_ref": "115-ФЗ, ст.6, п.2",
  "section": "Обязательный контроль операций с признаками структурирования",
  "category": "structuring",
  "text": "Операции подлежат обязательному контролю, если выявлены признаки намеренного разбиения суммы на несколько операций ниже порога...",
  "effective_from": "2024-01-01",
  "version": "2024-rev3"
}

### 3.4 Векторизация и индексация
* Embedding-модель: локальная (on-premise), например sentence-transformers/paraphrase-multilingual-MiniLM или аналог с поддержкой русского языка. Внешние embedding-API запрещены (NFR-10).
* Векторный индекс: хранится в локальной векторной БД (ChromaDB / FAISS / pgvector).
* Метаданные для фильтрации: rule_id, regulation_ref, category, effective_from — индексируются для пост-фильтрации результатов retrieval.

### 3.5 Формат source_ref
* source_ref в черновике отчёта формируется из метаданных чанка и указывает на конкретный пункт регламента:
* Формат: {regulation_ref} (например, 115-ФЗ, ст.6, п.2) или {regulation_ref} / {section} для детализации.
* Валидация (SR-12): каждый source_ref сверяется с существующими Rule.regulation_ref в базе знаний. Ссылка на несуществующий пункт отклоняется (Traceability Ratio = 100%, NFR-04).

## 4. Детализация evidence_ref (SR-14)
evidence_ref обеспечивает фактическую обоснованность (grounding, BR-05) — привязку каждого утверждения отчёта к конкретной транзакции и её реквизиту.

### 4.1 Структура evidence_ref
{
  "tx_id": "TX-7781",
}

* tx_id — идентификатор транзакции, существующей в Transaction (FK). Обязателен.
* field — имя поля транзакции, на которое ссылается утверждение. Обязателен.

### 4.2 Допустимые значения field
Поле field принимает значения из фиксированного перечня (соответствует атрибутам Transaction):
* amount — сумма операции
* currency — валюта
* counterparty — контрагент
* purpose — назначение платежа
* channel — канал операции
* status — статус транзакции
* timestamp — время операции

### 4.3 Правила валидации evidence_ref
* Существование tx_id: tx_id должен существовать в Transaction для клиента кейса. Несуществующий tx_id → утверждение отклоняется (SR-13).
* Допустимость field: field должен входить в фиксированный перечень (раздел 5.2). Недопустимое значение → ошибка валидации.
* Соответствие факта: значение поля, извлечённое из Transaction по tx_id + field, должно подтверждать fact_text утверждения (проверяется на этапе grounding, SR-13).
* Связь с UI (SR-16): tx_id + field передаётся в интерфейс для подсветки соответствующего фрагмента транзакционного лога.

### 4.4 Пример связки «утверждение → доказательство → нормативное обоснование»
{
  "fact_text": "Выявлено 12 транзакций по 95 000 ₽ в течение 3 дней (сумма ниже порога обязательного контроля)",
  "evidence_ref": { "tx_id": "TX-7781", "field": "amount" },
  "source_ref": "115-ФЗ, ст.6, п.2"
}

Здесь evidence_ref подтверждает факт данными транзакции (BR-05), а source_ref — нормативным пунктом (BR-04).

## 5. Индексы и производительность
Для обеспечения NFR-08 (сокращение времени агрегации ≥ 70%) рекомендуются следующие индексы:
* Transaction: составной индекс по (client_id, timestamp) — для быстрой выборки истории транзакций клиента за период (SR-03).
* Transaction: индекс по tx_id (PK) — для прямого доступа по evidence_ref.tx_id.
* Case: уникальный индекс по incident_id — для поиска кейса по внешнему ID (SR-01).
* Case: индекс по client_id — для выборки кейсов клиента.
* Rule: индекс по rule_id и regulation_ref — для валидации source_ref (SR-12).
* Векторный индекс: по embedding чанков базы знаний — для семантического поиска (SR-07).

## 6. Доступ к данным и безопасность
* Read-Only (BR-07, SR-17): все подключения к источникам (Client, Card, Transaction, Case) выполняются через сервисные учётные записи с правами только на чтение.
* Маскирование PII (NFR-09, 152-ФЗ): поля Client.full_name, Client.inn, Card.pan_masked маскируются в логах, трейсах и reasoning_trace. Полный PAN в PoC-контуре не хранится.
* Изолированный периметр (NFR-10): векторная БД и embedding-модель развёрнуты локально, без внешних вызовов.

## 7. Связь с другими артефактами
* SRS (раздел 5, JSON Schema): evidence_ref (раздел 5) и source_ref (раздел 4) настоящего документа являются источниками для полей JSON Schema черновика.
* BPMN To-Be: сущность Case и её статусы соответствуют шагам процесса (инициация → обработка → HITL → автоэкспорт).
* UML Sequence: участники SQL Tool и RAG Retrieval работают с сущностями Transaction/Client и Rule соответственно.
* Evaluation Plan: синтетические записи Transaction, Case, Rule формируют Golden Dataset для тестирования.
