# QA-сценарии: запуск и чтение результатов

Основная установка и полный рабочий цикл собраны в [единой инструкции](service-and-lab.md). Команды этого справочника выполняются из корня вашей копии. Упоминания сохранённых прогонов относятся к указанной дате; их локальные архивы не входят в обычный клон.

Актуально на 09.10.2026. Шаг 3 проверяет 15 зафиксированных примеров на исходном коде сервиса с учебными подменами embedding и Ollama. Docker, PostgreSQL, UI и настоящая модель для этой команды не нужны.

## 1. Прочитать сценарии

Откройте [каталог кейсов](../../qa/datasets/aml-v1/README.md). В таблице указаны вход, ожидаемый результат и выборка. Например:

- QA-S01: 12 операций по 95000.00 RUB → 1140000.00 RUB, 17 фактов.
- QA-S02: операция на начале окна включена, на конце — исключена.
- QA-S03: суммы USD и RUB раздельны; учитываются все статусы операций.
- QA-S14: инструкция в назначении платежа не попадает в модельный запрос и факты.
- QA-S15: после двух неверных ответов тестовой модели ожидается `VALIDATION_FAILED`.

`draft` означает черновик для проверки. `refusal` — отказ с указанной причиной. `error` — ошибка ввода или зависимости. Ожидаемый отказ считается успешно пройденным тестом, если получен правильный код и отсутствует запрещённый результат.

## 2. Выполнить проверку из VS Code

В терминале PowerShell:

```powershell
# Терминал открыт в корне вашей копии проекта.
& .\scripts\rebuild\Enter-LocalEnvironment.ps1
$qaResult = 'verification/qa-step-03-user-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B .\qa\tools\check_scenarios.py --output-dir $qaResult
if ($LASTEXITCODE -ne 0) { throw ('Проверка не пройдена; смотрите результаты: ' + $qaResult) }
Get-Content -LiteralPath (Join-Path $qaResult 'result.json') -Raw
```

Каждый запуск требует нового каталога результатов. Команда сначала проверяет JSON Schema, SHA256, связи снимков и эталонов, затем выполняет сценарии. Она не меняет обычную историю заданий, БД, Kafka и исходные данные. Сетевые подключения Python запрещены на время квалификации.

Для отдельной выборки добавьте `--split calibration` или `--split heldout`; без параметра проверяются обе. На этом этапе допускается проверка контрактов обеих выборок. При последующей настройке Judge используйте только calibration; heldout сохраняйте для отложенной оценки. Это организационное разделение открытых локальных файлов, а не скрытый внешний benchmark.

## 3. Разобрать файлы результата

| Файл | Что смотреть |
|---|---|
| `result.json` | Общий статус квалификации, `case_count`, семь семей происхождения и статус каждого кейса. В `issues` записаны причины расхождения; `events` показывают этапы обработки. |
| `replay.json` | Фактически наблюдавшиеся синтетические результаты и измеренное время этого локального прогона. Подходит текущему offline evaluator. |
| `replay-template.json` | Только ожидания, без результатов. Пустой `outcomes` не означает успешную проверку. |
| `evaluation.json` | Метрики evaluator и причины незавершённой продуктовой приёмки. |

Ожидаемый итог этого набора: `result.status=PASS`, `case_count=15`, `product_acceptance=INCOMPLETE`. Это разные уровни оценки. Первый подтверждает проверенные контракты сценариев. Второй остаётся незавершённым: нет реальной оценки модели, экспертной приёмки и необходимого набора независимых примеров.

Здесь используются простой учебный токенизатор, равные искусственные векторы и заранее заданные ответы модели. Записанные выбранные правила проверяют применение политики и версии источников; метрики такого прогона не измеряют качество ранжирования настоящего embedding. Время относится к локальным подменам, а не к SLA модели. M-02, M-03 и M-08 не подставляются из успешности автотестов.

## 4. Что делать при расхождении

Сохраните каталог результата и найдите `case_id` с `FAIL` или `ERROR`. Сравните его наблюдение из `replay.json` с ожиданием в [cases.json](../../qa/datasets/aml-v1/cases.json). Для обратной связи достаточно ID кейса, команды и `issues`/`error_type`.

Не меняйте ожидаемую сумму или код ради успешного прогона. Опубликованный пакет v1 проверяется по хешам. Пересмотр оформляется новой версией: причина, старое и новое ожидание, изменённые файлы и SHA256, дата/автор пересмотра и статус человеческой проверки. Пока эксперт не проверил набор, его статус остаётся `pending`. Предыдущие результаты сохраняются.

Не запускайте `build_fixtures.py` для обычного тестирования: это сохранённый одноразовый рецепт подготовки исходной версии, а не средство ремонта упавшего теста.
