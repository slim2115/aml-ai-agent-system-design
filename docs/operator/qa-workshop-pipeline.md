# Практикум QA: SQL, API и Kafka

Основная установка и полный рабочий цикл собраны в [единой инструкции](service-and-lab.md). Команды этого справочника выполняются из корня вашей копии. Упоминания сохранённых прогонов относятся к указанной дате; их локальные архивы не входят в обычный клон.

Шаг 10, 24.10.2026. Цель занятия — доказать результат обработки по связанным идентификаторам и объяснить поведение при повторах и сбоях. Сначала запишите ожидаемый результат упражнения, затем выполните его и сравните наблюдения. Примеры ниже — задания для собственного запуска, а не новые результаты квалификации.

Цепочка: Swagger → Kafka → обработчик → очередь PostgreSQL → AML workflow в SQLite → отчёт → проекция PostgreSQL и интерфейс. PostgreSQL хранит очередь, доставки и последнюю проекцию задания. Источником истины для задания, отчёта и решения оператора остаётся SQLite workflow. В этом занятии используются настоящий поиск и отчёт `template`; генерация LLM и Judge проверяются отдельно.

## Подготовка и отдельное подключение DBeaver

Нужны PowerShell 7 в VS Code, готовые `.venv`, локальная модель поиска с manifest, PostgreSQL, Docker Desktop с Linux engine и образом Kafka, Playwright/Chromium. Подготовьте **полный QA-стенд** командами раздела 1 [инструкции цепочки](qa-pipeline-quickstart.md#1-подготовить-полный-qa-стенд). Сохраните `$qaRunId` и `$qaBase`. Если он уже подготовлен, продолжайте с его идентификатором; новый `prepare` создаёт независимые данные. Браузерный стенд `browser_stand.py` для этого занятия не подходит.

Выполняется один QA-стенд и один прогон. Во время автоматического сценария не отправляйте ручные запросы и не меняйте службы. Для ручного разбора дождитесь завершения runner. Сценарии сами создают синтетические события и восстанавливают остановленные службы через `finally`.

| Инструмент | Для этого занятия | Обычный учебный стенд |
|---|---|---|
| Swagger | [127.0.0.1:18765/docs](http://127.0.0.1:18765/docs) | `127.0.0.1:8765/docs` |
| UI | [127.0.0.1:18501](http://127.0.0.1:18501) | `127.0.0.1:8501` |
| PostgreSQL | `127.0.0.1:56432`, `aml_qa_<суффикс запуска>` | `127.0.0.1:55432`, `aml_lab` |
| Kafka | `127.0.0.1:29092`, топики и группа своего QA-запуска | Обычные топики `aml.lab.*` |

Откройте установленный DBeaver. Создайте **отдельное** подключение PostgreSQL с именем `AML QA — <ваш run_id>`; готовые подключения «AML — просмотр» и «AML — практика» относятся к обычной БД. Для QA возьмите `host`, `port`, `database`, `roles.reader.user` и `roles.reader.password` из приватного `<qaBase>/lab-connection.json`. Используйте подготовленный локальный PostgreSQL-драйвер. Для ручного ввода выберите аутентификацию по пользователю/паролю; если копируете существующее подключение, удалите его команду получения пароля: обычный `Get-DBeaverPassword.ps1` выдаёт пароль другой БД. Здесь достаточно роли `reader`, Auto-commit и полного имени схемы в запросах.

Для Swagger возьмите `api_token` из того же файла: **Authorize**, ключ без `Bearer`, заголовок `X-Lab-Key`. Учётные данные не включайте в учебный отчёт. Порядок доступа описан в [инструкции QA-стенда](qa-stand-quickstart.md#доступ-к-swagger-и-sql).

Откройте новый SQL-редактор именно у QA-подключения и выполните:

```sql
SELECT current_database() AS database_name,
       current_user AS role_name,
       inet_server_addr() AS server_address,
       inet_server_port() AS server_port;
```

Ожидается ваша `aml_qa_<суффикс>`, роль `qa_<суффикс>_reader`, адрес `127.0.0.1`, порт `56432`. При другом результате смените подключение до продолжения. Все SQL-упражнения здесь — `SELECT`. Не меняйте роли, очередь, offset группы, схемы и снимок источников; сброс данных не требуется. Таблицы `practice.*` предназначены для самостоятельного SQL, но их изменения не меняют источники AML-отчёта.

## Как запускать одно упражнение

В таблице ниже выберите `$qaSuite` и `$qaCase`, затем выполните общий блок. Для каждого упражнения используйте новый каталог результата. `--prepare-model` подготавливает поиск из уже сохранённой модели; скачивания и вызова Ollama в этом профиле нет.

```powershell
# Терминал открыт в корне вашей копии проекта.
# $qaRunId и $qaBase уже получены при подготовке полного QA-стенда.
$qaSuite = 'chain'
$qaCase = 'test_01_real_chain_opens_exact_kafka_job_in_operator_ui'
$qaEvidence = 'verification/qa-workshop-pipeline-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B .\qa\tools\run_pipeline.py --run-id $qaRunId --output-dir $qaEvidence --suite $qaSuite --test $qaCase --prepare-model
$qaExitCode = $LASTEXITCODE
Get-Content -LiteralPath (Join-Path $qaEvidence 'result.json') -Raw
```

| Упражнение | `$qaSuite` | `$qaCase` | Наблюдения |
|---|---|---|---|
| 1. Событие → задание → отчёт | `chain` | `test_01_real_chain_opens_exact_kafka_job_in_operator_ui` | `QA-P01.json` |
| 2. Повторная публикация | `chain` | `test_02_identical_republication_has_two_deliveries_and_one_job` | `QA-P02.json` |
| 3. Конфликт одного UUID | `chain` | `test_03_conflicting_uuid_goes_to_dlq_without_changing_original` | `QA-P03.json` |
| 4. Повреждённый JSON | `chain` | `test_04_malformed_json_has_exact_dlq_source_and_no_inbox_entry` | `QA-P04.json` |
| 5. Остановка обработчика | `chain` | `test_05_broker_ack_while_worker_stopped_then_resumes_single_job` | `QA-P05.json` |
| 6. Потеря подтверждения commit | `faults` | `test_lost_kafka_commit_ack_preserves_intake_and_recovers` | `PF-05-commit-before.json`, `PF-05-commit-after.json` |
| 7. Бюджет SQL-ожидания | `faults` | `test_live_postgresql_query_respects_shared_budget` | `PF-06-live-sql-budget.json` |

Упражнение 6 запускает **два** варианта функции; остальные строки — по одной проверке. К `--test` нельзя добавлять `[before-commit]` или `[after-commit]`: runner принимает имя функции. `--suite all` используется без `--test`.

Для успеха нужны код выхода `0`, `status: PASS`, `collection_complete: true`, ожидаемое число проверок, `failure/error/skipped: 0`, `source_files_unchanged_during_run: true`. Отсутствующий `result.json` или `ERROR` означает незавершённую/неуспешную проверку. Не подменяйте результат данными предыдущего занятия.

Файл наблюдений читается так; для следующих упражнений замените имя файла:

```powershell
$qaObservation = Get-Content -LiteralPath (Join-Path $qaEvidence 'QA-P01.json') -Raw | ConvertFrom-Json
$qaObservation.observations | ConvertTo-Json -Depth 12
```

## 1. Связать событие, задание и отчёт

До запуска объясните, почему HTTP `202` не доказывает готовность отчёта. После запуска найдите `event_id`, исходные `topic/partition/offset`, `job_id`, `report_id`, `report_version`, `content_sha256`. В Swagger выполните `GET /lab/kafka/analyses/{event_id}`, затем `GET /v1/jobs/{job_id}` и `GET /v1/reports/{report_id}/reference?version=...`. Сравните идентификаторы, версию и хеш с `observations[].consistency`. Откройте событие в UI через «Запросы AML из Kafka» → «Открыть задание из Kafka».

В DBeaver выполните запросы 2, 3, 4 и 7 из [SQL-шпаргалки](../../qa/pipeline/queries.sql). В каждом замените нулевой UUID на **свой `event_id`**, оставив одинарные кавычки и `::uuid`. Нулевое значение — заглушка, пустой результат с ним ожидаем. Здесь используется обычный SQL-литерал; `%s` из Python и `:event_id` без настройки параметров DBeaver вставлять не нужно. В приложении такие значения передаются параметрами драйвера, а не конкатенацией строки SQL.

**Решение:** `broker_acknowledged` подтверждает запись в Kafka. Готовность доказывает `succeeded` конкретного задания и совпадение ссылки на отчёт, версии и `content_sha256`. У `QA-P01` дополнительно проверены SQLite и открытие этого же задания/отчёта в Chromium. PostgreSQL-проекция может временно отставать, поэтому разовое несовпадение нужно проверить повторно и сопоставить с API. `canonical_sha256` относится к событию; `content_sha256` — к отчёту. Хеширование `job_json::text` не воспроизводит канонизацию приложения.

## 2. Доказать отсутствие второго задания при повторе

Предскажите количество запросов, сохранённых Kafka-позиций и заданий. Запустите упражнение 2. Возьмите его `event_id` и выполните запрос 5 шпаргалки. Запишите `stored_kafka_positions`, `duplicate_publications`, `projected_job_count`; сравните две тройки координат в `QA-P02.json`.

Для ручного повторения после автоматического прогона отправьте в Swagger новое событие через `POST /lab/kafka/analyses`: новый UUID, `engine: template`, `synthetic: true`, окно из `<qaBase>/config/demo-policy.json`. Сохраните всё отправленное тело. Дождитесь отчёта и отправьте **то же тело** ещё раз. Для этой пары повторов UUID и `occurred_at` должны оставаться прежними. Сверьте SQL и API по новому UUID.

**Решение:** автоматический сценарий даёт одну строку запроса, две разные Kafka-позиции, одну повторную публикацию и одно спроецированное задание. В доставках — `duplicate: false`, затем `true`. Агрегация считает `COUNT(d.event_id)`, поскольку `COUNT(*)` после `LEFT JOIN` посчитает и строку без доставки. SQL доказывает состояние проекции; `consistency.workflow_admissions: 1` и `stored_reports: 1` отдельно подтверждают отсутствие второго admission/отчёта в SQLite. Это идемпотентный эффект на стороне приложения, а не обещание единственной доставки Kafka.

## 3. Отличить повтор от конфликта

Предскажите, что произойдёт при прежнем `event_id` и изменённом `occurred_at`. Выполните упражнение 3 и сравните `original_source`, `rejected_source`, `dlq_records[].source`, `reason_code`, `original_unchanged`. По SQL проверьте прежний `job_id` и одну сохранённую доставку.

**Решение:** новое содержимое с тем же UUID даёт `EVENT_CONFLICT` в DLQ. Координаты `rejected_source` должны совпасть с `source` соответствующей записи DLQ. Исходный запрос и отчёт не меняются; отклонённая позиция не добавляется в `analysis_deliveries`. Это отличие от упражнения 2: совпадения одного UUID недостаточно, важно равенство канонического события.

## 4. Найти повреждённое сообщение в DLQ

Предскажите, сможет ли Swagger передать невалидные байты JSON в Kafka. Выполните упражнение 4. Найдите `source`, совпадающую тройку в `dlq_records`, `reason_code`, `value_bytes`, `inbox_unchanged`, `jobs_unchanged`.

**Решение:** HTTP-валидация не пропускает такой JSON, поэтому сценарий публикует байт `{` напрямую в собственный QA-топик. DLQ содержит `INVALID_EVENT`, `value_bytes: 1` и исходные координаты. Очередь и задания не меняются. `probe_id` — метка опыта, **не `event_id` невалидного сообщения**; его нельзя использовать для выдуманной связи с заданием. Корреляция здесь — точные `topic/partition/offset`. Offset сам по себе не уникален между топиками и разделами. Проверка читает новые DLQ-записи отдельным наблюдателем без commit рабочей группы; обычные команды сброса offset для занятия не нужны.

## 5. Проверить восстановление обработчика

Предскажите ответ API, когда Kafka доступна, а обработчик остановлен. Выполните упражнение 5 и найдите наблюдения `worker: stopped`, `publication`, `no_inbox_observations`, `result_code`, `worker: restored`, итоговую `consistency` и `new_job_count`.

**Решение:** публикация получает `broker_acknowledged`; пока обработчик остановлен, очередь ещё пуста, а чтение результата возвращает `404 / AML_REQUEST_NOT_FOUND`. После восстановления тот же `event_id` даёт одно задание и отчёт. Проверка не требует создавать новый UUID для «зависшего» запроса. Если сам процесс теста принудительно завершён, `finally` может не выполниться: проверьте `stand.py status --run-id $qaRunId` и журналы своего QA-запуска перед продолжением.

## 6. Различить повтор публикации и повтор доставки

Выполните упражнение 6. Для каждого файла сравните `ack.offset`, `committed_before`, `committed_after`, `fault_boundary`, `recovered_job_id`. В варианте `before` найдите `actual_redelivery`. По UUID каждого опыта выполните запросы 3 и 5 шпаргалки.

**Решение:** до commit позиция группы не продвигается; после восстановления наблюдается повторная доставка **той же Kafka-позиции**. В таблице доставок остаётся одна строка: её ключ — `(topic, partition, offset_value)`. После реального commit позиция равна `ack.offset + 1`, несмотря на искусственно потерянное подтверждение. В обоих вариантах сохранённая очередь доводится до одного задания. Ошибка вводится до/после вызова настоящего commit на границе клиента; это не измерение физического обрыва сети. В упражнении 2 выполнялись две публикации с разными координатами, поэтому там было две строки доставок.

## 7. Проверить ограничение ожидания SQL

Предскажите, будет ли вызывающий код ждать все 10 секунд. Выполните упражнение 7 и прочитайте `budget_seconds`, `simulated_sql_seconds`, `elapsed_seconds`, `outcome`, `scope`. Не запускайте `pg_sleep` вручную в обычной учебной БД.

**Решение:** проверка выполняет настоящий `SELECT pg_catalog.pg_sleep(10)` с общим бюджетом 2,2 с. Ожидаются `BudgetExpired`, закрытое соединение, время вызывающего кода от 1,5 до менее 4 с и успешный следующий `SELECT 1`. Это проверка предела ожидания и освобождения соединения; она не доказывает мгновенную отмену SQL на сервере и не задаёт SLA полного AML-анализа.

## Полный прогон и самостоятельный отчёт

Выборочные упражнения помогают разобраться в механике. Для полного набора выполните отдельный прогон из **12 проверок**:

```powershell
$qaEvidence = 'verification/qa-workshop-pipeline-all-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B .\qa\tools\run_pipeline.py --run-id $qaRunId --output-dir $qaEvidence --suite all --prepare-model
$qaExitCode = $LASTEXITCODE
Get-Content -LiteralPath (Join-Path $qaEvidence 'result.json') -Raw
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py status --run-id $qaRunId
```

Полный набор также проверяет недоступность API, PostgreSQL и брокера, потерю ответа HTTP после реального `202`. Их точные границы перечислены в [инструкции сценариев](qa-pipeline-quickstart.md#3-что-проверяют-сценарии). При `503 / publication: unknown` сохраните и повторите исходное тело с тем же UUID: отсутствие ответа не доказывает отсутствие записи в Kafka.

Составьте короткий отчёт по каждому упражнению: ожидание; путь к новому `result.json`; фактический статус и число тестов; файл наблюдений; связанные идентификаторы и координаты; один SQL-вывод; объяснение результата. Для ошибки добавьте ожидаемое/фактическое поведение и код из результата, не копируя приватную конфигурацию. Успешная инфраструктурная цепочка с `template` не подтверждает фактическую точность настоящей LLM, принятие отчёта оператором или готовность сервиса к промышленной эксплуатации.

После занятия остановите именно свой QA-запуск:

```powershell
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py stop --run-id $qaRunId
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py status --run-id $qaRunId
```

Ожидается `status: stopped`, `data: retained` в ответе `stop`. Данные и артефакты остаются для разбора. Для продолжения используйте прежний `run_id`; для независимого нового опыта сначала остановите текущий стенд, затем создайте новый. SQL-сброс обычного `aml_lab` и удаление Kafka volume для этих упражнений не требуются.
