# Практикум QA: от запуска до объяснения результата

Основная установка и полный рабочий цикл собраны в [единой инструкции](service-and-lab.md). Команды этого справочника выполняются из корня вашей копии. Упоминания сохранённых прогонов относятся к указанной дате; их локальные архивы не входят в обычный клон.

Работайте в терминале VS Code, PowerShell 7, в `.`. Это маршрут шага 10. У каждого опыта должны быть команда, фактический результат и ссылка на свидетельство. Успех автотеста и качество модели оцениваются отдельно.

## Выбрать занятие

| Занятие | Что сделать | Где выполнять | Что сохранить |
|---|---|---|---|
| 1. Прочитать итог | Найти PASS приложения, FAIL Judge и отсутствие человеческой калибровки | Общий отчёт (локальный материал: `verification/qa-step-09-2026-10-23/report-qualified/report.html`) | Три статуса и причины |
| 2. Проверить поле | Выполнить один тест, затем два учебных теста; добавить свою проверку | [Playwright](qa-workshop-browser.md) | JUnit, имя теста, ожидаемое значение |
| 3. Найти дефект | Включить неверную сумму, разобрать trace, повторить без дефекта | [Playwright](qa-workshop-browser.md) | FAIL с trace и отдельный PASS после восстановления |
| 4. Проследить событие | Найти event → job → report в API, SQL и UI | [SQL/API/Kafka](qa-workshop-pipeline.md) | Идентификаторы и SQL-результат своего прогона |
| 5. Проверить повтор | Доказать один эффект при двух доставках | [SQL/API/Kafka](qa-workshop-pipeline.md) | Координаты двух сообщений, один job |
| 6. Разобрать сбои | Poison/DLQ, восстановление worker, тайм-аут | [SQL/API/Kafka](qa-workshop-pipeline.md) | Причина отказа, состояние после восстановления |
| 7. Сравнить модель | Сравнить template, два повтора LLM и факты | [Модели](qa-workshop-models.md) | Числители, знаменатели и версии |
| 8. Проверить оценщика | Найти подменённую сумму, ошибку цитаты и усечённый ответ Judge | [Модели](qa-workshop-models.md) | Исходный факт, кандидат, причина ошибки |
| 9. Добавить кейс | Дописать тест в отдельном учебном browser-наборе и выполнить регрессию | [Playwright](qa-workshop-browser.md) | Новый тест и отдельный результат полного профиля |
| 10. Объяснить итог | Собрать отчёт и сформулировать, что доказано и что осталось неизвестным | [Отчёты и CI](qa-reporting-quickstart.md) | HTML/JSON и краткое заключение |

Начните с занятий 1–3; для них не нужны Docker, PostgreSQL и настоящие модели. Занятия 4–6 требуют полного изолированного QA-стенда. Не запускайте его одновременно с браузерным стендом: они используют одни QA-порты. Обычный сервис и учебный SQL-стенд имеют отдельные данные.

## Расследования Dark Factory в интерфейсе аналитика

Дополнительно доступен практикум этапа 9: шесть разборов готовых фактов с открытой рубрикой. Он подходит для занятия без Docker, моделей и живой БД. Команды выполняются из корня проекта, после установки `.venv-ci` по основной инструкции:

```powershell
$learningRun = 'learning-' + (Get-Date -Format yyyyMMdd-HHmmssfff)
.\.venv-ci\Scripts\python.exe -I -B qa/tools/build_investigations.py --run-id $learningRun
if ($LASTEXITCODE -ne 0) { throw 'Подготовка не завершена; сохраните каталог для разбора' }
.\.venv-ci\Scripts\python.exe -I -B -m streamlit run qa/analyst/app.py --server.address 127.0.0.1 --server.port 8502 --server.headless true --browser.gatherUsageStats false
```

В [UI на 8502](http://127.0.0.1:8502) выберите «Учебные расследования», свой пакет и случай. Последовательно разберите сохранённый FAIL после исправления, неизвестные токены, пропущенный повтор, зависимые измерения, изменённое свидетельство и повтор HTTP после потери ACK. Для каждого выберите вывод, причину, следующий шаг и подтверждающие факты; обоснование запишите своими словами. Нажмите «Проверить разбор» и скачайте JSON ответа. [Полная инструкция с упражнениями и диагностикой](service-and-lab.md#quality-investigations).

PASS показывает соответствие открытой учебной рубрике. Свободный текст не оценивается, знания человека не измеряются. Если текущий код отличается от снимка пакета, оценка блокируется до создания нового пакета. Не подменяйте этим упражнением живые Kafka/LLM-проверки, человеческую калибровку или приёмку продукта.

## Как вести запись

Скопируйте [шаблон журнала](../../qa/workshop/session-template.json) в новый каталог:

```powershell
# Терминал открыт в корне вашей копии проекта.
$qaSession = 'var/qa/workshop/session-' + [guid]::NewGuid().ToString('N')
New-Item -ItemType Directory -Path $qaSession | Out-Null
Copy-Item -LiteralPath 'qa/workshop/session-template.json' -Destination (Join-Path $qaSession 'notes.json')
```

В `notes.json` заполняйте записи по мере выполнения. `not_started` заменяйте на `observed` только после собственного запуска или просмотра указанного сохранённого свидетельства. Укажите `mode`: `live` или `saved_evidence`. Это ваш учебный журнал, а не независимая экспертная разметка Judge и не подтверждение производственной приёмки.

Для каждого опыта ответьте на четыре вопроса:

1. Какое утверждение я проверяю?
2. Какое наблюдение опровергло бы его?
3. Что получилось фактически и где это записано?
4. Какое объяснение поддерживают данные и чего этот опыт не доказывает?

Не заменяйте первый FAIL повторным PASS: храните оба каталога. Поломка стенда до выполнения теста — это ошибка запуска, а не обнаруженный бизнес-дефект. Если нового измерения не было, укажите дату сохранённого результата.

## Быстрый разбор общей сводки без запуска служб

```powershell
$qaReport = Get-Content -LiteralPath 'verification/qa-step-09-2026-10-23/report-qualified/report.json' -Raw | ConvertFrom-Json
$qaReport.profiles | Select-Object id, status
$qaReport | Select-Object status, evidence_integrity, product_acceptance
```

Ожидается пять PASS, Judge FAIL и человеческая калибровка INCOMPLETE. `evidence_integrity=PASS` говорит о согласованности входов по хешам. Это не одобрение ошибочных ответов Judge. Все 11 допустимых оценок совпали с учебными метками, но допустимы только 11 ответов из 20: нельзя отбросить девять ошибок из знаменателя.

## Как подтвердить свой новый тест

Сначала выполните его отдельно по browser-инструкции, затем весь учебный набор и основной профиль. После изменений runner или общей логики запустите программную регрессию в новый каталог:

```powershell
& .\scripts\rebuild\Enter-LocalEnvironment.ps1
$qaRegression = 'var/checks/workshop-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B scripts/rebuild/run_checks.py --output-dir $qaRegression
if ($LASTEXITCODE -ne 0) { throw 'Регрессия не пройдена; сохраните каталог результатов' }
Get-Content -LiteralPath (Join-Path $qaRegression 'unit-verification.json') -Raw
```

Эта регрессия проверяет код и контракты с подменами зависимостей; browser-набор запускается отдельно. Полный чистый CI и формирование его отчёта описаны в [инструкции](qa-reporting-quickstart.md). Не подставляйте старый результат в недостающий этап нового прогона.

## Когда занятие закончено

У вас есть исходное ожидание, наблюдаемый дефект, причина, подтверждение восстановления и ссылки на оба результата. Для Kafka дополнительно есть доказательство числа эффектов, для моделей — версии и ограничения выборки. Новый тест проходит вместе с относящейся к нему регрессией. Стенд остановлен штатной командой с вашим `run_id`.

Человеческая калибровка Judge отложена по вашему решению. Удалённый GitHub Actions подтверждается отдельным запуском после вашего commit/push. Учебный журнал не закрывает эти условия автоматически.
