# Локальный выпуск, обновление и откат

Основная установка и полный рабочий цикл собраны в [единой инструкции](service-and-lab.md). Команды этого справочника выполняются из корня вашей копии. Упоминания сохранённых прогонов относятся к указанной дате; их локальные архивы не входят в обычный клон.

Историческая процедура локального ZIP-выпуска от 01.10.2026. Первый выпуск — **`0.1.0-local.1`**, архив исходного кода для уже подготовленного локального стенда Windows x64 / Python 3.12. Автоматического развёртывания нет. Commit, push и публикацию на GitHub выполняет владелец проекта.

Для текущей полной поставки используйте `scripts/release/publication_files.py` и точные списки `docs/publication/*.txt`. Старый ZIP-сборщик не включает весь позднее добавленный QA-контур; его PASS подтверждает целостность выбранного архива. Команды публикации текущего rebuild включены в раздел 11 основной инструкции. Приведённый ниже ZIP-процесс сохранён для разбора истории выпусков.

## Что входит в выпуск

В ZIP находятся код, тесты, инструкции, зафиксированные зависимости, синтетические данные, учебный SQL и локальные ресурсы Swagger. Файл `release-manifest.json` содержит SHA-256 и размер каждого включённого файла; соседний `.zip.sha256` — SHA-256 всего архива. Проверка обнаруживает повреждение или несоответствие содержимого, но не заменяет подпись издателя.

Архив **не содержит** `.venv`, модели, Ollama, PostgreSQL, пароли и API-ключ, базы/отчёты/журналы из `var`, Git и прежние аудиторские доказательства из `verification`. Это не самостоятельный установщик. Текущие сценарии определяют корень своей копии; новую копию необходимо отдельно подготовить по основной инструкции.

## Собрать и проверить архив

В PowerShell 7 из терминала VS Code:

```powershell
# Терминал открыт в корне вашей копии проекта.
& .\.venv\Scripts\python.exe -I -B scripts\release\package_release.py build
& .\.venv\Scripts\python.exe -I -B scripts\release\package_release.py verify .\var\releases\aml-ai-agent-system-0.1.0-local.1-source.zip
```

Ожидается JSON с `status: PASS`. Сборщик не меняет установленный сервис и не запускает серверы. Он откажется перезаписывать существующий выпуск. Для новой редакции сначала измените версию в `.rebuild/release-version.json`; для повторной проверки неизменного кода укажите другой пустой `--output-dir`. Перед публикацией используйте результаты CI именно для той же редакции исходников. Сам факт сборки ZIP не означает, что тесты прошли.

## Обновить существующий стенд вручную

Сейчас код этого выпуска уже находится в рабочем каталоге: устанавливать его поверх самого себя не требуется. Порядок ниже — для следующего проверенного выпуска, без миграции схемы БД.

1. Завершите задания и SQL-сессии. Остановите Streamlit через **Ctrl+C** в его терминале и стенд через `.\scripts\lab\Stop-Lab.ps1`. Закройте отдельные CLI-запуски AML. Дождитесь завершения процессов; копировать работающий PostgreSQL-кластер или SQLite с активной записью нельзя.
2. Сохраните **полную копию** папки `.` в отдельной папке вне проекта. Проверьте свободное место и завершение копирования. В резервной копии должны быть `.venv`, `var/workflow`, `var/postgres`, `var/models`, `var/tools` и `.rebuild`. Такая копия содержит ваши данные и секреты: храните её локально, не добавляйте в Git и не публикуйте как релиз.
3. Проверьте новый ZIP командой `package_release.py verify <путь-к-архиву>` и распакуйте его **в новую пустую папку для просмотра**, не в действующий проект. Сохраните ZIP вместе с `.sha256`. Сопоставьте новый `release-manifest.json` с предыдущим, прочитайте описание изменений и ограничений.
4. Перенесите согласованные файлы исходников из новой папки в `.`. Удалённые в новом выпуске исходники нужно сверить по двум манифестам и убрать отдельно, иначе они останутся от старой версии. **Не заменяйте** `.venv`, `var`, `.git`, `verification` и исторические файлы `.rebuild`; из `.rebuild` обновляется только `release-version.json`. `origin.json` сохраняет происхождение существующей установки. Не используйте зеркалирование всей папки: отсутствующие в ZIP базы и модели должны сохраниться.
5. Если изменились файлы зависимостей, установите их в существующее окружение из проверенных локальных wheels. Для текущего формата lock-файлов команда ниже проверяет все SHA-256. Если нужного wheel нет, остановитесь и подготовьте его отдельно; не запускайте устаревшие скрипты квалификации блоков, которые перезаписывают старые доказательства.

```powershell
& .\scripts\rebuild\Enter-LocalEnvironment.ps1
& .\.venv\Scripts\python.exe -I -B -m pip --isolated install --no-index --only-binary=:all: --require-hashes --find-links .\var\wheelhouse\windows-py312 --find-links .\var\lab-downloads -r .\requirements\windows-py312.lock -r .\requirements\lab-extra-windows-py312.lock
& .\.venv\Scripts\python.exe -I -B -m pip check
```

6. Выполните `.\scripts\ci\Test-Ci.ps1`: скрипт создаст отдельное чистое окружение и выполнит текущий CI. Если для новой версии отсутствуют локальные тестовые wheels, используйте явный параметр `-UsePackageIndex`, как описано в [инструкции CI](../rebuild/ci-cd.md). Затем запустите сервис по `service-quickstart.md`: получите `ready` и один учебный отчёт по `INC-000123`, проверьте старую историю. Запустите стенд по `sql-api-quickstart.md`, проверьте `GET /lab/status` и `SELECT * FROM practice.clients;`. Проверьте сохранность своей учебной заметки. Резервную копию сохраняйте до окончания проверки.

Этот порядок сохраняет существующий каталог и данные. Он не является автоматизированной установкой. Если будущий выпуск меняет схему PostgreSQL/SQLite, ему нужны отдельные миграция, резервирование и проверенный откат: одного копирования исходников недостаточно.

## Откатить обновление

1. Остановите оба сервиса и все задания так же, как перед обновлением.
2. Сохраните неудачную установку и её журналы в отдельную папку для разбора. Не смешивайте её файлы с резервной копией.
3. Восстановите полную резервную копию в **тот же** путь `.`, включая `.venv` и `var`. Это возвращает согласованные код, зависимости и состояние обеих БД на момент резервирования. Путь важен для venv и маркеров владения PostgreSQL.
4. Повторите проверку запуска из пункта 6. Записи, сделанные после резервирования, в восстановленных БД отсутствуют; при необходимости их разбирают по сохранённой копии неудачной установки.

Автоматический откат не настроен; описанная процедура ещё не является результатом испытания восстановления реального пользовательского состояния. Архив текущего выпуска и его проверки фиксируются отдельно в `verification/ci-release-2026-10-01/release`.
