# SQL, API и Kafka: проверка полной цепочки

Основная установка и полный рабочий цикл собраны в [единой инструкции](service-and-lab.md). Команды этого справочника выполняются из корня вашей копии. Упоминания сохранённых прогонов относятся к указанной дате; их локальные архивы не входят в обычный клон.

Инструкция для **PowerShell 7 в терминале VS Code**, актуальна на **19.10.2026**. Шаг 5 завершён: полный живой набор **12/12 PASS**, итоговая квалификация **16/16 PASS**. Результат и границы проверки (локальный материал: `verification/qa-step-05-2026-10-17/summary.md`). QA-стенд остановлен с сохранением данных; для собственной практики выполните команды ниже.

Здесь используются настоящие QA API, Kafka, PostgreSQL, SQLite и локальная модель поиска. Отчёт формируется в режиме `template`: Ollama, генерация LLM, LLM Judge и оценка экспертом в этот профиль не входят. PostgreSQL хранит очередь и копию состояния задания; источником истины для задания, отчёта и решения оператора остаётся SQLite workflow.

## 1. Подготовить полный QA-стенд

Нужны готовые `.venv`, PostgreSQL, Docker Desktop с Linux engine и уже загруженным образом Kafka. Playwright и Chromium устанавливаются один раз по [инструкции шага 4](qa-playwright-quickstart.md#1-установить-инструменты-один-раз). Запуск тестов сам подключает эти инструменты из `var/qa/tooling`; ручная установка пакетов в `.venv` не требуется.

Для поиска нужна уже сохранённая модель `paraphrase-multilingual-MiniLM-L12-v2` и её manifest в `var/models`. Параметр `--prepare-model` загружает её в память и подготавливает индекс по QA-источникам; он не скачивает модель и не изменяет её файлы.

Одновременно работает **один QA-стенд и один прогон**. Перед этим шагом остановите браузерный стенд шага 4 его командой `browser_stand.py stop --run-id СОХРАНЁННЫЙ_ID`. Для текущей цепочки нужен полный стенд `stand.py`; идентификатор браузерного стенда здесь не подходит. Подробности изоляции и учётных данных приведены в [инструкции шага 2](qa-stand-quickstart.md).

```powershell
# Терминал открыт в корне вашей копии проекта.
$qaDescription = & .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py prepare
if ($LASTEXITCODE -ne 0) { throw 'Не удалось подготовить QA-стенд' }
$qaStand = $qaDescription | ConvertFrom-Json
$qaRunId = $qaStand.run_id
$qaBase = $qaStand.data_directory
$qaRunId

& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py start --run-id $qaRunId
if ($LASTEXITCODE -ne 0) { throw 'Стенд не запущен; проверьте status и журналы' }
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py status --run-id $qaRunId
```

Сохраните **возвращённый** `run_id`. Для продолжения в новом терминале восстановите переменные, подставив его:

```powershell
# Терминал открыт в корне вашей копии проекта.
$qaRunId = 'ВСТАВЬТЕ_СОХРАНЁННЫЙ_RUN_ID'
$qaBase = Join-Path (Get-Location) ('var\qa\runs\' + $qaRunId)
```

Ожидается `postgres_running: true`, `broker.status: ready` и `true` для `api`, `ui`, `worker`, `review-worker` в `services`. Поиск на этом этапе может быть ещё не подготовлен.

| Компонент | Адрес только для QA |
|---|---|
| Интерфейс оператора | [127.0.0.1:18501](http://127.0.0.1:18501) |
| Swagger | [127.0.0.1:18765/docs](http://127.0.0.1:18765/docs) |
| PostgreSQL | `127.0.0.1:56432`; БД и роли из описания своего запуска |
| Kafka | `127.0.0.1:29092`; топики и группы своего запуска |

Ключ Swagger и пароли находятся в приватном `<qaBase>/lab-connection.json`. Для SQL используйте роль `reader` или `student`, для Swagger — ключ `X-Lab-Key`; порядок подключения описан в [шаге 2](qa-stand-quickstart.md#доступ-к-swagger-и-sql). Не включайте ключи, пароли и этот файл в отчёты или снимки экрана.

## 2. Запустить цепочку, затем проверки сбоев

Каталог результата всегда **новый**. Во время прогона не отправляйте ручные запросы и не переключайте службы этого QA-стенда: проверки выполняются последовательно и используют общую очередь. Защита запуска запрещает второй одновременный прогон.

Сначала выполните пять сценариев цепочки:

```powershell
$qaEvidence = 'verification/qa-pipeline-chain-user-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B .\qa\tools\run_pipeline.py --run-id $qaRunId --output-dir $qaEvidence --suite chain --prepare-model
$qaExitCode = $LASTEXITCODE
Get-Content -LiteralPath (Join-Path $qaEvidence 'result.json') -Raw
```

`chain` — профиль по умолчанию; `--prepare-model` разрешает подготовку поиска, если он ещё не готов. Без этого параметра неподготовленный поиск даст `QA_SEARCH_NOT_READY_USE_PREPARE_MODEL`. Уже готовая модель используется повторно.

Затем выполните семь сценариев сбоев:

```powershell
$qaEvidence = 'verification/qa-pipeline-faults-user-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B .\qa\tools\run_pipeline.py --run-id $qaRunId --output-dir $qaEvidence --suite faults --prepare-model
$qaExitCode = $LASTEXITCODE
Get-Content -LiteralPath (Join-Path $qaEvidence 'result.json') -Raw
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py status --run-id $qaRunId
```

Для полного повторного прогона используйте `--suite all`: пять сценариев цепочки и семь сценариев сбоев, **12 проверок**. Число проверок описывает состав набора, а не результат его выполнения. Успех подтверждается кодом выхода `0`, `status: PASS`, `collection_complete: true`, отсутствием провалов, ошибок и пропусков в результате именно вашего прогона.

Для разбора одного сценария укажите точное имя функции:

```powershell
$qaEvidence = 'verification/qa-pipeline-one-user-' + [guid]::NewGuid().ToString('N')
& .\.venv\Scripts\python.exe -I -B .\qa\tools\run_pipeline.py --run-id $qaRunId --output-dir $qaEvidence --suite chain --prepare-model --test test_02_identical_republication_has_two_deliveries_and_one_job
```

`--test` работает с `chain` или `faults`, но не с `all`. Для функции проверки Kafka commit запускаются оба её варианта: до и после реального commit. Успех выбранной функции не заменяет полный прогон.

## 3. Что проверяют сценарии

| Сценарий / файл наблюдений | Ожидаемое поведение |
|---|---|
| `QA-P01` — полная цепочка | API публикует событие; Kafka подтверждает запись; обработчик сохраняет очередь в PostgreSQL, создаёт AML-задание и проецирует результат. Playwright открывает именно это задание и отчёт в UI. Сверяются API, PostgreSQL, SQLite, версия и SHA256 отчёта. |
| `QA-P02` — повтор того же события | Две публикации одинакового тела с одним `event_id` дают две позиции Kafka, одну запись запроса и одно AML-задание. Вторая новая доставка помечена `duplicate: true`. |
| `QA-P03` — конфликт UUID | То же `event_id` с изменённым содержимым уходит в DLQ с `EVENT_CONFLICT`; исходный запрос, задание и отчёт сохраняются. |
| `QA-P04` — повреждённый JSON | Невалидные байты публикуются прямо в собственный QA-топик, поскольку HTTP-валидация их не пропустит. Проверяется DLQ с `INVALID_EVENT`, исходные координаты и отсутствие нового запроса/задания. |
| `QA-P05` — остановленный обработчик | API возвращает подтверждение Kafka, хотя записи очереди и задания ещё нет. После запуска обработчика возникает одно задание для исходного события. |
| `PF-01-api-outage` | При недоступном API событие остаётся `queued` с `NOT_READY`. После восстановления и подготовки поиска обрабатывается тот же запрос. |
| `PF-02-postgresql-outage` | При остановленной QA PostgreSQL событие нельзя сохранить; Kafka offset не подтверждается. После восстановления обработка продолжается. Вызов обработчика сообщения в этой проверке выполняется из процесса теста. |
| `PF-03-broker-outage` | Недоступность брокера даёт `503`; подтверждение публикации может быть неизвестно. Повторяется исходное тело с тем же UUID, затем проверяется согласованный результат. |
| `PF-04-http-ack-lost` | После настоящего HTTP `202` тест однократно отбрасывает ответ на границе клиента. Повтор с тем же ключом `kafka-aml:<event_id>` возвращает то же задание. Это управляемая подмена на границе клиента, а не физический обрыв сети. |
| `PF-05-commit-before` и `PF-05-commit-after` | Ошибка вводится до или после настоящего Kafka commit. Проверяются сохранённая очередь, позиция группы и восстановление. В варианте «до» подтверждается повторная доставка той же позиции без второго задания. |
| `PF-06-live-sql-budget` | Настоящий `SELECT pg_sleep(10)` ограничен общим бюджетом ожидания 2,2 с; проверяются выход по бюджету, закрытие соединения и доступность следующего SQL-запроса. |

Проверки сбоев останавливают только службы собственного QA-запуска и восстанавливают их через `finally`. Если сам процесс теста аварийно завершён или восстановление не удалось, сверьте `status` и журналы до нового прогона. Обычные службы не останавливайте.

Бюджет планировщика **10 с** ограничивает его HTTP/SQL-операции. Это технический предел ожидания одного прохода, а не SLA анализа и не гарантия длительности полного цикла Kafka `poll`. Закрытие PostgreSQL-соединения по бюджету также не доказывает мгновенную отмену запроса на стороне сервера.

## 4. Повторить цепочку руками в Swagger и SQL

Делайте это после завершения автоматического прогона. Проверьте `GET /v1/readiness`: нужен готовый поиск. Подготовку можно запросить через `POST /v1/readiness`, затем снова прочитать состояние.

1. В Swagger откройте `POST /lab/kafka/analyses`. Используйте пример контракта, `engine: template`, `synthetic: true` и **новый UUID** в `event_id`. Окно `window` должно совпадать с политикой `<qaBase>/config/demo-policy.json`; сохраните отправленное тело для возможного повтора.
2. Ответ `202` с `broker_acknowledged` означает только запись в Kafka. Запишите `event_id`, `topic`, `partition`, `offset`. Это ещё не готовый отчёт.
3. Выполняйте `GET /lab/kafka/analyses/{event_id}`. Пока обработчик не записал очередь, возможен `404` с `AML_REQUEST_NOT_FOUND`; после приёма появятся `queued`, затем `submitted` и итоговый статус. При длительном ожидании смотрите обработчик и DLQ, а не создавайте новый UUID для того же запроса.
4. Выполните запросы из [SQL-шпаргалки](../../qa/pipeline/queries.sql), подставив свой UUID. Сопоставьте запись запроса и доставки с ответами API. `job_json` — последняя проекция задания; она может отставать от workflow.
5. По `job_id` прочитайте `GET /v1/jobs/{job_id}`. При `succeeded` возьмите `result.report_id` и `result.report_version`; запросите `GET /v1/reports/{report_id}?version=...` и `GET /v1/reports/{report_id}/reference?version=...`. Во втором ответе версия и `content_sha256` должны совпасть с PostgreSQL.
6. Откройте UI → «Запросы AML из Kafka» → нужный `event_id` → «Открыть задание из Kafka». Проверьте идентификаторы задания и отчёта. Готовый черновик ещё требует проверки оператором.
7. Отправьте **точно сохранённое тело** повторно. Сохраните второй offset и убедитесь: доставок стало две, `event_id`, `job_id`, версия и хеш отчёта сохранились. Для самостоятельного нового опыта создавайте новый UUID.

При `503` и `publication: unknown` нельзя считать, что сообщение точно не дошло. Повторяйте исходное тело с исходным UUID; изменение `occurred_at` тоже меняет событие и может вызвать конфликт.

Таблицы `practice.*` позволяют тренироваться в SQL, но их редактирование **не меняет источники AML-отчёта**. Анализ использует отдельный неизменяемый снимок источников QA-запуска. PostgreSQL не заменяет SQLite workflow; SQL-соединение между ними в шпаргалке не имитируется. Сравнение с workflow выполняется через API или автоматическую проверку.

## 5. Прочитать результат и остановить стенд

В новом каталоге прогона находятся:

- `result.json`, `tests.xml`, `pytest.log` — итог, JUnit и журнал pytest;
- `preparation.json`, `run.json`, `source-hashes.json` — подготовка поиска, параметры запуска и контроль файлов;
- `QA-P*.json`, `PF-*.json` — идентификаторы, координаты Kafka и наблюдения по выполненным сценариям;
- `QA-P01-ui-trace.zip` и, если удалось сохранить, `QA-P01-ui-failure.png` — только при сбое браузерного сценария.

Если выполнение прервалось до итогового `result.json`, такой прогон не завершён. Если есть `ERROR`, отсутствие ожидаемых тестов или изменение файлов во время выполнения, результат нельзя считать успешным. Не редактируйте исходники во время прогона. Для просмотра trace используйте локальную команду из [инструкции Playwright](qa-playwright-quickstart.md); не загружайте артефакты с локальными данными на сторонние сайты.

Журналы служб: `<qaBase>/logs/api.log`, `worker.log`, `review-worker.log`, `postgres.log`, `ui.log`. Пример:

```powershell
Get-Content -LiteralPath (Join-Path $qaBase 'logs\worker.log') -Tail 60
```

`PROTOCOL_ERROR` / `WORKFLOW_PROTOCOL_ERROR` означает несовместимый или повреждённый ответ workflow: обработчик останавливается, а очередь и уже известный `job_id` сохраняются. Сначала проверьте API, его журнал и исходное задание. После устранения причины выполните штатные `stop`, затем `start` **того же QA-запуска**, снова подготовьте поиск и повторите проверку с новым каталогом результатов. Не удаляйте очередь и не заменяйте UUID, чтобы скрыть ошибку.

После практики:

```powershell
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py stop --run-id $qaRunId
& .\.venv\Scripts\python.exe -I -B .\qa\tools\stand.py status --run-id $qaRunId
```

В ответе `stop` ожидается `status: stopped`, `data: retained`. Следующий `status` должен показать `false` для всех служб в `services` и для `postgres_running`; брокер не готов. Данные, очередь и история сохраняются. Для продолжения используйте `start` с тем же `run_id`; для независимого опыта — новый `prepare` после подтверждённой остановки текущего стенда.
