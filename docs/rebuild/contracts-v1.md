## Канонический источник и граница блока

- Канонические модели нового контракта: `src/contracts/v1.py`.
- Производные артефакты: `contracts/v1/schema.json` и `contracts/v1/openapi.json`.
- JSON Schema генерируется из моделей; её не следует исправлять независимо от кода.
- HTTP-описание имеет формат OpenAPI 3.1; наличие файла не означает работающий API.
- Модели ещё не подключены к старому `src/schemas.py`, графу, UI и источникам данных.
- Старые модели, примеры и runtime сохраняют прежнее поведение до отдельной миграции.
- Реального HTTP-сервера, аутентификации и постоянного хранилища этот блок не создаёт.
- Совместимость потребителей требует явной миграции; v1 не является прозрачным адаптером.

Pydantic предоставляет генерацию JSON Schema из моделей и адаптеров типов:
[официальная документация](https://docs.pydantic.dev/latest/concepts/json_schema/).
OpenAPI описывает HTTP-интерфейс и его схемы, а не реализацию исполнения:
[спецификация OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0).

## Общие правила формата

1. Версия контракта задаётся явно в версионируемых конвертах.
2. Вложенные структуры типизированы; неизвестные поля запрещены.
3. Отсутствующее значение, `null` и пустой массив имеют разный смысл.
4. Не допускается молча заменять `null` массивом или удалять неизвестные поля.
5. Тип JSON-поля важен: строковое число не заменяет обязательное JSON-число.
6. Невалидный payload не становится валидным отчётом за счёт потери его разделов.

`incident_id` имеет вид `INC-[0-9]{6}`: ровно 10 ASCII-символов.
Пробелы по краям и завершающий перевод строки не обрезаются и не принимаются.
Отсутствующее значение, `null`, пустая или состоящая из пробелов строка дают
`MISSING_INPUT`; неверный тип либо другой формат — `INVALID_INPUT_FORMAT`.
Проверка входа должна предшествовать чтению источников в будущем runtime.
ASCII и отсутствие trim — явные решения нового контракта, а не описание старого SRS.

Денежное значение передаётся десятичной строкой, без промежуточного float.
Допустимый лексический формат задаётся канонической схемой.
Это сохраняет точность суммы, но не определяет правила округления и конвертации.
Код валюты задаётся отдельным полем; его синтаксис не доказывает применимость валюты.
ISO-код сам по себе не задаёт курс, дату пересчёта или разрешённую валюту порога.

## Время, окно и версия данных

Моменты времени передаются как RFC 3339 с явным `Z` или числовым смещением.
Поддерживается подмножество: заглавные `T`/`Z`, не более 6 знаков доли секунды,
календарно допустимые даты; leap second `:60` не принимается.
Datetime без timezone отклоняется; календарная дата остаётся отдельным типом.
`as_of` фиксирует момент расследования, а не время чтения UI или повторного запроса.
Окно отбора имеет полуоткрытые границы `[start, end)`:
операция ровно на `start` включается, ровно на `end` исключается.
Порядок границ и допустимость окна проверяются отдельно от наличия этих полей.

Контекст и результат связываются с идентификатором и версией snapshot.
`captured_at` означает момент сборки снимка для запроса; v1 требует `as_of <= captured_at`.
Это консервативное техническое ограничение, не утверждённый срок свежести источников.
Возраст отдельных источников и разрешённое использование ранее собранного снимка
требуют отдельной политики; наличие позднего `captured_at` свежесть не доказывает.
Evidence должно разрешаться в том же снимке, который использован для отчёта.
Версия снимка не доказывает автоматически согласованность файлов разных источников.
Будущий builder должен проверять состав снимка, обновления и устаревание данных.
Длительность окна, политика timezone источников и допустимая свежесть остаются pending.
Исходным timestamp без зоны нельзя молча назначать UTC или локальную зону машины.

## Структурированные доказательства

Evidence — объединение вариантов с явным тегом вида доказательства.
Транзакционный вариант ссылается на `tx_id` и поле из разрешённого перечня.
Профильный вариант ссылается на клиента и разрешённое поле профиля.
Агрегатный вариант описывает операцию, исходные элементы и вычисленный результат.
Теги v1: `transaction`, `profile`, `sum`, `count`; произвольные операции не принимаются.
Для воспроизводимости агрегата должны быть известны его область и снимок данных.

Профильные и агрегатные ссылки расширяют буквальную формулировку SR-14.
Это расширение фиксируется в новом контракте, без объявления исторического SRS исправленным.
Факт содержит обязательный `sources: list[RuleCitation]`; список может быть пустым.
Пустой список означает отсутствие нормативной ссылки у факта, а не отсутствие evidence.
Нормативная ссылка должна идентифицировать проверяемый источник и его редакцию.
Наличие идентификатора источника не доказывает смысловую применимость правила.

Отдельные семантические проверки будущего runtime:

- ссылка существует и принадлежит разрешённому контексту клиента;
- указанное поле соответствует значению, на котором основано утверждение;
- набор агрегата не содержит повторного учёта одной операции;
- сумма, количество и другие операции имеют правильные типы и единицы;
- пересчёт валют имеет утверждённые основания; без них смешанная сумма не подтверждена;
- текст утверждения не теряет существенных ограничений исходных данных.

## Результат расследования

Результат — строгое tagged union по `status`: `draft`, `refusal` или `error`.
Каждый вариант имеет собственный набор допустимых полей.
`draft` содержит факты, паттерны и правила в форме, заданной канонической моделью.
Для него требуются `data_completeness=full` и явная версия политики оценки.
Это структурное условие допуска, а не подтверждение утверждённости самой политики.
Только `draft` имеет обязательное поле `confidence`: JSON-число от 0 до 1 включительно
или `null`, если оценка не измерена. В блоке 4 дорелизный контракт уточнён:
`null` заменяет выдуманную численную уверенность; поле по-прежнему нельзя опускать.
Текущий runtime всегда возвращает `null`. Клиенты должны учитывать nullable-тип;
производные JSON Schema и OpenAPI обновлены. Это не экспертная оценка,
вероятность нарушения или разрешение действий.

`refusal` содержит причину отказа и разрешённые метаданные.
Он не содержит фактов, паттернов, применимых правил и иных отчётных выводов.
Даже пустые отчётные массивы не должны подменять отсутствие запрещённых разделов.
`error` описывает техническую ошибку; отчётные разделы в нём также запрещены.
Ошибка исполнения и предметная недостаточность данных остаются разными исходами.
Служба должна преобразовывать исключения в безопасный текст по коду ошибки;
сырые `ValidationError`, входной payload и PII нельзя помещать в ответ или логи.
Статус конверта не может противоречить варианту вложенного результата.

Наблюдаемые события и краткое проверяемое обоснование отделены от текста отчёта.
Контракт не требует предоставления скрытых рассуждений модели.
Причины недостаточности, конфликтов и выбора правил требуют предметной политики.

## Задания и отмена

Состояния job: `queued`, `running`, `succeeded`, `refused`, `failed`,
`cancelled`, `timed_out`.
Терминальные состояния: все перечисленные после `running`.
Терминальное состояние неизменно; повторное расследование создаёт новое задание.
Поле `result` допускается только для `succeeded`, `refused` и `failed`:
соответственно вариант `draft`, `refusal` или `error`.
У `queued`, `running`, `cancelled` и `timed_out` результата расследования нет.

Принятая отмена переводит задание в сохраняемое терминальное состояние `cancelled`.
Подтверждение этого состояния не доказывает физическую остановку вызова LLM.
Будущий worker обязан отбросить поздний результат после отмены или истечения срока.
Проверку перехода и запись состояния необходимо выполнять атомарно в runtime.
Гонка отмены с завершением разрешается проверкой текущей версии/состояния.

Общий бюджет исполнения должен учитывать retries и ожидания, используя monotonic clock.
UTC timestamp срока полезен для обмена, но не заменяет monotonic deadline процесса.
Warmup/readiness, ожидание в очереди и время до отображения различаются в измерениях.
Согласование single-run SLA и p95 остаётся открытым; новый порог не вводится.

## Решения человека и доставка

Запрос решения содержит действие, основание и данные проверки ожидаемой версии.
Автор, роль, timestamp, идентификаторы решения и аудита должны формироваться сервером.
Их будущим источником служит доверенный контекст аутентификации, а не текст LLM или UI.
Сохраняемое решение связано с конкретными incident/report/version/hash.
Историческое решение не переписывается при появлении новой версии отчёта.
Идемпотентность повторов и optimistic concurrency требуют хранилища и атомарной проверки.

Решение, подпись, доставка и финальный статус кейса — отдельные сущности процесса.
Одобрение само по себе не означает подпись, экспорт или разрешённое закрытие кейса.
Доставка имеет сохраняемые состояния `pending`, `delivered`, `failed`.
Запрос и запись доставки всегда содержат `job_id`; `report` и `decision_id` nullable.
Для `manual_queue` оба поля могут быть `null`, чтобы маршрутизировать отказ по заданию.
Для `export` Python-валидатор требует непустые `report` и `decision_id`.
Для `delivered` требуется положительная квитанция с совпадающими `delivery_id`,
`job_id`, `report` (включая `null`), назначением, операцией и режимом интеграции.
Timeout, отрицательная квитанция и локальная имитация не подтверждают реальную доставку.
Повторы отправки и callback должны обрабатываться идемпотентно.
Владелец финального статуса и контракт внешней CMS/очереди пока не утверждены.

В блоке 2 представлены только модели решений и квитанций.
Auth, durable storage, CAS, подпись и реальные адаптеры реализуются позже.
Rate limits, PII guards и сетевой периметр также не обеспечиваются одной моделью.

## Планируемый HTTP-интерфейс

| Метод и путь | Успех | Смысл ответа |
| --- | --- | --- |
| `POST /v1/jobs` | 202 | Задание принято, выдан `job_id` |
| `GET /v1/jobs/{job_id}` | 200 | Текущее состояние и допустимый результат |
| `POST /v1/jobs/{job_id}/cancel` | 200 | Состояние после обработки отмены |
| `POST /v1/reports/{report_id}/decisions` | 201 | Создано решение по версии отчёта |
| `GET /v1/decisions/{decision_id}` | 200 | Сохранённое решение |
| `POST /v1/deliveries` | 202 | Запрос доставки принят |
| `GET /v1/deliveries/{delivery_id}` | 200 | Состояние доставки и квитанция |

202 подтверждает принятие работы, не успешное расследование или доставку.
Python-вызов модели не является HTTP-запросом и не подтверждает эти статусы.

| Код | Категория |
| --- | --- |
| 400 | Отсутствующий или невалидный вход |
| 404 | Неизвестный ресурс |
| 409 | Конфликт идемпотентности, версии или состояния |
| 401 / 403 | Нет аутентификации / недостаточно полномочий |
| 503 | Сервис ещё не готов принимать работу |

## Совместимость и пределы проверок

Из прежних моделей сохраняются предметные понятия и применимые перечисления.
Это не означает автоматического преобразования старого `AMLInvestigationDraft` в v1.
Старые nullable-массивы, timestamp без зоны и формат evidence мигрируются явно.
Потребителям нельзя молча разрешать прежние поля отказа либо терять неизвестные поля.
Синтаксическая JSON Schema и семантические Python/runtime-проверки — разные уровни.
`TypeAdapter` проверяет форму и валидаторы моделей; он не вызывает `semantics.py`.
Временная согласованность job/result и incident проверяются через `validate_job`.
Согласованность двух состояний, ревизии и терминальность — через `validate_job_transition`.
Проверка отчёта относительно контекста требует отдельного `validate_report_context`.
Она повторно проверяет вложенные списки перед разрешением ссылок: `frozen=True`
сам по себе не делает список неизменяемым. Конфликтующие версии одной цитаты запрещены.
`canonical_digest` использует SHA-256 от UTF-8 JSON (`sort_keys=True`, без пробелов,
`ensure_ascii=False`, `allow_nan=False`); это локальный рецепт v1, не подпись и не JCS.
Hash отчёта вычисляется по проверенному payload без самого поля hash; служба должна
сохранять эти байты и проверять ссылки на них при решениях и доставке.
Сервис обязан вызвать нужные проверки перед записью и публикацией результата.
Не вся межполевая логика, переходы состояний и предметные инварианты выражены в Schema.
Валидация формы не доказывает grounding, полномочия, атомарность или реальную доставку.

Открытые предметные решения перечислены в `config/domain-policy-pending.json`.
Это ограниченный реестр относящихся к контрактам вопросов, не замена всех R-01…R-16.
Его записи имеют статус `pending`; значения нормативных политик не выдумываются.
