# CI и локальные выпуски

Актуально на 23.10.2026. Все изменения находятся в отдельной копии `.`. Коммиты и push выполняет владелец проекта. Добавлен отдельный Chromium smoke и общий формат отчётов; [профили CI](qa-ci-profiles.md), [инструкция оператора](../operator/qa-reporting-quickstart.md).

## Что проверяет CI

`.github/workflows/ci.yml` запускается при push, pull request и вручную через GitHub Actions. Профиль: Windows x64, CPython 3.12, новое виртуальное окружение. `requirements/ci-windows-py312.lock` фиксирует версии и SHA-256 всех 62 тестовых зависимостей, включая Streamlit, FastAPI, HTTP-клиенты и драйвер PostgreSQL. Тяжёлые библиотеки моделей в этот набор не входят.

Последовательность основного задания: установка по хешам → `pip check` → проверка конфигурации CI и точного набора установленных пакетов → проверка актуальности контрактов → pytest → отдельная квалификация интерфейса, SQLite и локальной доставки. Производные схемы сравниваются с сохранёнными файлами, а не перезаписываются.

Выбор тестов задаётся в `pyproject.toml`: contracts, configuration, evaluator, eval, runtime, workflow, lab, release. API проверяется через внутрипроцессный клиент с подменой БД; Streamlit — через AppTest и подменённый обработчик. Процессные проверки действительно запускают дочерние процессы Windows. Любой сбой или пропуск теста приводит к неуспеху проверки.

Основной отчёт публикуется в `windows-ci-results`. Второе задание запускает один детерминированный Chromium smoke с настоящими UI/API и SQLite и публикует `windows-browser-results`. Выгружаются очищенные отчёты, а не конфигурации подключений, базы, сырые логи или traces. PostgreSQL, Kafka, embedding, Ollama и Judge остаются отдельными явными локальными проверками; зелёный CI не подтверждает качество модели или экспертную AML-приёмку.

## Повторить на этой машине

В терминале VS Code используйте PowerShell 7:

```powershell
# Терминал открыт в корне вашей копии проекта.
& .\scripts\ci\Test-Ci.ps1
```

По умолчанию используются уже скачанные пакеты из `var/wheelhouse/ci-windows-py312`; сеть не нужна. Каждый запуск создаёт новое окружение в `var/verification/ci/<время>` и сохраняет результаты в `var/checks/ci-local/<время>`. Рабочая `.venv`, данные сервиса и старые свидетельства аудита не заменяются. Путь результатов выводится в терминал, итог находится в `summary.json`.

Если локального набора пакетов нет, загрузку точных версий из PyPI можно выбрать явно:

```powershell
& .\scripts\ci\Test-Ci.ps1 -UsePackageIndex
```

Можно указать другой установленный CPython 3.12 x64 через `-PythonPath 'C:\путь\python.exe'`. Другие версии Python и платформы не входят в проверенный профиль. Скрипт сохраняет новое тестовое окружение и логи для разбора, поэтому повторные запуски расходуют место на диске.

## После вашего push

Поместите содержимое доработанного проекта в корень выбранного Git-репозитория: workflow должен лежать в корневой `.github/workflows/`, а не внутри вложенной папки `rebuild`. Не добавляйте `.venv`, `.venv-ci`, `var`, локальные ключи или резервные копии данных. Старые проект и аудит не требуется перезаписывать для локальной проверки.

После push откройте GitHub → Actions → **Rebuild Windows CI**. Для подтверждения нужны успешный завершённый запуск на вашем commit SHA и его артефакт результатов. Локальный PASS сам по себе не доказывает успех удалённого запуска. Проверьте автоматический запуск для push и pull request; ручной запуск доступен через Run workflow после появления workflow в основной ветке.

## Выпуск и обновление

Подготовлен инструмент локального версионированного архива исходников и проверки целостности. Архив не содержит установленные библиотеки, модели, базы, ключи и личные результаты. Он предназначен для уже подготовленного локального окружения; это не автономный установщик.

Порядок упаковки, проверки, обновления и отката описан в [инструкции по выпускам](../operator/release-update.md). Автоматической публикации в GitHub Releases или установки на компьютер пока нет. Развёртывание сохраняет ручной контроль владельца.
