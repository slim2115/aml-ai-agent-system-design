# Профили QA в CI

Обновлено: 23.10.2026. [Workflow](../../.github/workflows/ci.yml) содержит два независимых задания Windows/Python 3.12 на `push`, `pull_request` и ручной `workflow_dispatch`. Это конфигурация для будущего запуска после вашего коммита и push. Локальные проверки файлов и тестов не подтверждают выполнение GitHub Actions.

| Задание | Что проверяет | Что запускает |
|---|---|---|
| `hermetic-windows` | Контракты, конфигурацию, полный изолированный набор тестов, операторский сценарий Streamlit AppTest | `.venv-ci`; API-клиенты внутри процесса, заглушки БД и моделей |
| `browser-smoke-windows` | Один сценарий `test_template_job_finishes_and_shows_exact_sources`: создание шаблонного задания и проверка точных источников в интерфейсе | Настоящий headless Chromium, отдельные локальные UI/API-процессы и SQLite; детерминированный обработчик |

PostgreSQL, Kafka, retrieval, генератор LLM и Judge проверяются отдельными явными локальными командами. Browser smoke не измеряет качество модели и не подтверждает работу Kafka-транспорта. Права workflow ограничены чтением репозитория; секреты и собственный постоянно работающий runner не нужны. Автоматический деплой и расписания не добавлены.

## Установка и запуск браузерного профиля

Задание создаёт `.venv`, поскольку существующий владелец QA-стенда запускает дочерние службы именно из `.venv/Scripts/python.exe`. Приложение получает зависимости из `requirements/ci-windows-py312.lock` с проверкой SHA256 и только готовыми wheels. Это отдельная среда свежего runner; локальная установленная среда пользователя не переустанавливается этими командами.

`browser_tooling.py install` проверяет отдельный `qa/requirements-browser.lock`, ставит инструменты в `var/qa/tooling/browser-python`, скачивает Chromium в `var/qa/tooling/browsers` и проверяет запуск браузера. Версия Python-пакета Playwright и SHA256 wheels фиксированы; соответствующая ревизия Chromium определяется поставляемыми Playwright метаданными. Отдельного lock с SHA256 архива Chromium нет. Браузерный кэш между заданиями не переносится.

`run_ci_browser.py` выполняет последовательность:

1. Создаёт новый принадлежащий прогону QA-профиль с синтетическими данными и временными локальными учётными данными.
2. Запускает только UI/API через существующий `browser_stand` на `127.0.0.1:18501/18765`.
3. В отдельном процессе вызывает существующий `run_browser.py` с одним точным тестом, без повторов и без инъекции дефекта; лимит процесса — 300 секунд.
4. В `finally` останавливает принадлежащие профилю службы, в том числе при ошибке старта или теста, и проверяет результат остановки. Ошибка очистки делает итог `FAIL`.
5. Сохраняет новый `result.json` со статусом теста и отдельным `cleanup_status`. Существующие результаты не перезаписываются.

Принудительное завершение runner или процесса извне может помешать выполнению `finally`; очистка не обещается при таком завершении. Следующий job использует свежий размещённый GitHub runner. Локально после прерывания сначала проверьте/остановите свой QA-профиль обычным `browser_stand`, не завершайте чужие процессы на портах.

На уже подготовленной локальной машине (из корня проекта, при свободных QA-портах):

```powershell
.\.venv\Scripts\python.exe -I -B qa/tools/run_ci_browser.py --output-dir var/qa/ci-browser-manual-01
python -I -B qa/tools/report_ci.py --profile browser --input-dir var/qa/ci-browser-manual-01 --output-dir var/checks/browser-report-manual-01
```

Имена выходных папок должны быть новыми. Устанавливать зависимости и Chromium при каждом локальном повторе не требуется. Инструкция по подготовке инструментов и полному профилю находится в [руководстве Playwright](../operator/qa-playwright-quickstart.md).

## Результаты и ограничения

После тестов оба задания вызывают `report_ci.py` с `if: always()`, затем добавляют `summary.md` в `GITHUB_STEP_SUMMARY` и сохраняют только каталог отчёта на 14 дней. Сбой тестов сохраняет красный статус job; `continue-on-error` не используется. Если подготовка остановилась до измерения, отчёт должен показать неполные доказательства, а не успешный тест.

В upload входят только сформированные и проверенные сборщиком безопасные отчёты: `report.json`, `summary.md`, `report.html`, `index.json` и явно разрешённые им результаты. Каталоги `var/qa/runs`, конфигурации подключений, runtime БД, browser traces, снимки экрана и служебные логи целиком не загружаются. Проверка секретов перед публикацией — дополнительный барьер; не добавляйте сырой каталог стенда в `upload-artifact`.

Локальный browser envelope: `profile=browser`, `status=PASS|FAIL|INCOMPLETE`, числовые `testcases/failure/error/skipped`, `cleanup_status=PASS|FAIL|NOT_STARTED`, `browser_result_path` относительно корня проекта, `run_id`, `selected_test`, `pytest_exit_code`. Путь ссылается на исходное измерение существующего browser runner; счётчики не заменяют JUnit и исходные результаты. `PASS` требует ровно один успешный тест без пропусков и успешную остановку. Пустой/повреждённый результат, другой тест, подмена профиля или изменение исходников во время теста не считаются успехом.

Реальные ошибки Judge из шага 8 остаются в отдельной оценке качества. Зелёный CI с модельными заглушками не отменяет их и не означает готовность LLM к работе без проверки человеком.

## Основания конфигурации

Официальная [документация Playwright Python по CI](https://playwright.dev/python/docs/ci) описывает установку браузеров и запуск pytest в CI; [документация браузеров](https://playwright.dev/python/docs/browsers) объясняет связь пакета с поддерживаемыми браузерными сборками. GitHub описывает [условия `always()`](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions), [резюме через `GITHUB_STEP_SUMMARY`](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands) и [загрузку артефактов](https://docs.github.com/en/actions/tutorials/store-and-share-data). Источники проверены 23.10.2026; существующие major-версии GitHub actions сохранены, их обновление не включено в эту доработку.
