# Практика HTTP и Swagger

Запустите стенд по [основной инструкции](../README.md), откройте <http://127.0.0.1:8765/docs> и нажмите **Authorize**. Значение `X-Lab-Key` находится в поле `api_token` локального файла `var/postgres/lab-connection.json`. Ключ действует для одного локального оператора; это учебная авторизация. Вводится сам ключ, без `Bearer`.

В Swagger раскройте метод, нажмите **Try it out**, заполните параметры и нажмите **Execute**. Интерфейс покажет запрос, код ответа, заголовки и JSON. Выполняйте упражнения последовательно. [exercises.http](exercises.http) содержит те же запросы; установка HTTP-клиента не нужна для работы в Swagger. Если ваш редактор поддерживает REST Client и переменные окружения, задайте `AML_LAB_API_KEY` в окружении процесса редактора. Не сохраняйте настоящий ключ в файле примеров.

Данные `/lab/*` находятся в PostgreSQL, в схеме `practice`. SQL-изменения этой схемы сразу видны в API. Схема `reference` содержит эталон для сравнения. Значения сумм передаются строкой, например `"95000.00"`, чтобы сохранять точность. Временные метки содержат часовой пояс, ответы нормализованы к UTC (`Z`).

| № | Упражнение | Что проверить |
|---|---|---|
| 1 | До авторизации выполните `GET /health`, затем `GET /lab/clients`; авторизуйтесь и повторите второй запрос. | `/health` возвращает `200` даже без ключа; защищённый запрос — `401 UNAUTHORIZED`, затем `200`. Health проверяет HTTP, доступность БД проверяет `/lab/status`. |
| 2 | Получите клиентов с `limit=2, offset=0`, затем с `offset=2`. Найдите выбранного клиента через `/lab/clients/{client_id}`. | Страницы имеют устойчивый порядок. Сопоставьте с `SELECT ... ORDER BY client_id LIMIT 2 OFFSET 2` в SQL. |
| 3 | Получите `/lab/cards?client_id=C-00045`, `/lab/incidents?client_id=C-00045` и `/lab/rules`. | Связь карты и инцидента с клиентом; у правил есть версии. Это синтетические правила для упражнений. |
| 4 | Отберите транзакции `INC-000123` в RUB, с `min_amount=95000.00`, `max_amount=95000.00`, между `2026-07-10T09:00:00Z` и `2026-07-11T10:00:00Z`. | Начало включено, конец исключён. Фильтр инцидента выбирает его клиента; окно времени задаётся отдельно. Сравните с SQL. |
| 5 | Создайте заметку через `POST /lab/notes`, сохраните `id` и `revision`; прочитайте её через `GET /lab/notes/{note_id}` и через SQL. | `201 Created`, заголовок `Location`, серверные timestamps, `revision=1`. Повторный POST создаёт другую заметку: сохраните ответ до повтора. |
| 6 | Измените заметку через PATCH с `expected_revision=1`, затем повторите PATCH с той же ревизией. | Первый ответ `200`, новая ревизия `2`; повтор — `409 VERSION_CONFLICT`, сохранённый текст не изменился. Перед дальнейшей правкой прочитайте текущую версию. |
| 7 | Отправьте `limit=101`, дату без часового пояса или сумму `0.001`; попробуйте заметку для отсутствующего инцидента. | `400 INVALID_INPUT_FORMAT`. В ответе безопасный код и `correlation_id`, без SQL, паролей и исходного текста ошибки драйвера. |
| 8 | Попробуйте DELETE заметки с устаревшей ревизией `1`, затем с актуальной `2`; прочитайте удалённую заметку. | Сначала `409`, затем `204` с пустым телом; после удаления GET возвращает `404 NOT_FOUND`. |

Для упражнения 4 на исходном наборе ожидается `TX-7700`. После ваших SQL-изменений ответ может отличаться. В упражнении 7 `INC-999999` отсутствует в исходном наборе; если вы создали его сами, выберите другой отсутствующий идентификатор.

Учебные заметки не являются AML-решениями, одобрениями отчётов или подтверждениями доставки. API разрешает запись только в `case_notes`; более широкие SQL-эксперименты выполняются ролью `aml_student` в `practice`.

## Дополнительно: ранее реализованный процесс AML

Методы `/v1/*` используют отдельное SQLite-хранилище процесса и фиксированные файлы демонстрационных данных. Они не запускают анализ изменённых таблиц `practice`. SQL и заметки доступны без модели.

`GET /v1/readiness` сообщает готовность, `POST /v1/readiness` явно начинает подготовку локальной модели эмбеддингов и индекса. Подготовка может занять заметное время. Создание задания требует `demo=true`, заголовка `Idempotency-Key` и точного окна демонстрационной политики. Образец запроса и окна описан в `config/demo-policy.json` и OpenAPI. По умолчанию выбран `engine=template`; `local-model` дополнительно требует готовой Ollama. Детали процесса и ограничения — в `docs/rebuild/workflow-runtime.md`.

Проверка HTTP-границы `/v1` проведена с настоящим хранилищем процесса и подменённым вычислительным worker в тестах; проверки SQL/API стенда не означают нового прогона реальной LLM через HTTP.
