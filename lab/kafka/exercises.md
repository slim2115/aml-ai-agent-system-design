# Практика: Swagger → Kafka → обработчик → PostgreSQL

Сначала выполните [инструкцию запуска](../../docs/operator/kafka-quickstart.md). Используйте только синтетические данные. Для каждого упражнения сохраняйте `event_id`, ответ API и результат SQL: это позволит сопоставить отправку и обработку.

В запросах ниже заменяйте `ВАШ_UUID` на идентификатор конкретного события. SQL выполняется после `scripts/lab/Open-Sql.ps1`; команды PowerShell — после выхода из SQL через `\q`. Новое учебное событие получает новый UUID; повторная отправка сохраняет всё исходное тело.

## 1. Пройти полный цикл

1. Отправьте событие через **POST /lab/kafka/events** в Swagger, как в инструкции запуска.
2. Зафиксируйте HTTP-код, `event_id`, раздел и смещение из подтверждения отправки.
3. Дождитесь строки `processed` в терминале обработчика.
4. Найдите результат:

```sql
SELECT event_id, incident_id, occurred_at, processed_at, topic, partition,
       offset_value, result_json
FROM kafka_lab.processed_events
WHERE event_id = 'ВАШ_UUID'::uuid;
```

**Ожидается:** одна строка. Объясните своими словами, почему ответ API `202` ещё не доказывает наличие этой строки.

## 2. Повторная отправка и уникальный результат

Отправьте через Swagger **точно то же тело** ещё два раза. Дождитесь обработки и выполните:

```sql
SELECT count(*) AS result_count
FROM kafka_lab.processed_events
WHERE event_id = 'ВАШ_UUID'::uuid;

SELECT topic, partition, offset_value, duplicate, recorded_at
FROM kafka_lab.deliveries
WHERE event_id = 'ВАШ_UUID'::uuid
ORDER BY partition, offset_value;
```

**Ожидается:** один результат и три обработанные позиции Kafka, из них две с `duplicate = true`, если все три отправки подтвердились и обработались. Дедупликация результата не удаляет сообщения из Kafka.

Повторная доставка уже обработанной позиции при сбое может не добавить строку в `deliveries`: ключ этой таблицы — `topic + partition + offset_value`. Таблица учитывает позиции, а не число всех попыток чтения.

## 3. Остановить обработчик и увидеть очередь

1. Нажмите **Ctrl+C** в терминале обработчика. Kafka и API оставьте работающими.
2. Отправьте три события с разными UUID через Swagger.
3. Убедитесь, что API возвращает `202`, а SQL пока не находит новые результаты.
4. В PowerShell выполните:

```powershell
.\scripts\kafka\Broker.ps1 -Action Lag
```

5. Запустите обработчик снова:

```powershell
.\scripts\kafka\Run-Worker.ps1
```

6. Повторите проверку `Lag` в другом терминале и найдите три результата SQL-запросом.

**Ожидается:** после обработки отставание возвращается к нулю при отсутствии других отправок. События пережили остановку обработчика благодаря хранению в Kafka. Выполняйте опыт в пределах срока хранения сообщений.

## 4. Порядок событий и разделы

Последовательно отправьте три события с новыми UUID и одним `incident_id = INC-000123`, каждый раз дожидаясь ответа предыдущего POST. Запишите их UUID в порядке отправки.

```sql
SELECT event_id, incident_id, partition, offset_value
FROM kafka_lab.processed_events
WHERE event_id IN ('ПЕРВЫЙ_UUID'::uuid, 'ВТОРОЙ_UUID'::uuid, 'ТРЕТИЙ_UUID'::uuid)
ORDER BY partition, offset_value;
```

**Ожидается:** одинаковый раздел и возрастающие смещения в порядке отправки. Значение `incident_id` используется как ключ Kafka. Смещения могут иметь промежутки из-за других сообщений и повторов. Поле `occurred_at` — время события; Kafka не сортирует сообщения по нему.

Найдите другой существующий инцидент запросом `SELECT incident_id FROM reference.incidents ORDER BY incident_id;` и повторите отправку для него. **GET /lab/incidents** читает `practice`, которая после SQL-упражнений может отличаться от исходного набора `reference`, используемого Kafka. Раздел может совпасть: разные ключи не обязаны попадать в разные разделы. Порядок гарантируется внутри одного раздела; общего порядка между разделами нет.

## 5. Валидация до Kafka

В Swagger отправьте тело без обязательного `event_id` или с `synthetic = false`.

**Ожидается:** ошибка валидации API; новое событие не отправляется в Kafka. Сравните этот случай со следующим упражнением: не каждое неверное тело обязано попадать в DLQ.

## 6. Неверное сообщение внутри Kafka и DLQ

Вернитесь в PowerShell и отправьте специально подготовленное учебное сообщение в обход API:

```powershell
.\scripts\kafka\Broker.ps1 -Action PublishInvalid
```

Дождитесь `dead_lettered` с причиной `INVALID_EVENT` в терминале обработчика. Прочитайте топик ошибок:

```powershell
.\scripts\kafka\Broker.ps1 -Action ReadDlq
```

**Ожидается:** запись с кодом причины и исходными `topic`, `partition`, `offset`. Поля `value_base64` и `key_base64` содержат ограниченную диагностическую копию исходного сообщения. В `processed_events` результат для него не создаётся.

Смещение исходного сообщения фиксируется только после подтверждения записи в DLQ. При сбое между этими действиями в DLQ возможны повторы с одним ключом исходной позиции.

## 7. Один UUID и разные данные

Возьмите событие из упражнения 1. Сохраните `event_id`, но измените `occurred_at` на другое допустимое UTC-время, затем отправьте его через Swagger.

После обработки проверьте исходную строку в `processed_events` и DLQ командой `ReadDlq`.

**Ожидается:** исходный результат сохранён, а конфликтующая запись обработана как `EVENT_CONFLICT`. Повтор одного UUID с изменёнными данными не считается безопасным повтором. Исправленное новое событие должно получить новый UUID.

## 8. Отказ брокера и неопределённая отправка

Остановите обработчик через **Ctrl+C**, затем остановите Kafka:

```powershell
.\scripts\kafka\Broker.ps1 -Action Stop
```

Отправьте новое событие из Swagger и сохраните его полное тело. **Ожидается:** ограниченное ожидание и `503`. Снова запустите Kafka, затем обработчик:

```powershell
.\scripts\kafka\Broker.ps1 -Action Start
```

```powershell
.\scripts\kafka\Run-Worker.ps1
```

Повторите исходное тело. Найдите результат SQL-запросом. Для данного опыта остановленный брокер обычно не принимает сообщение, но при сетевом обрыве подтверждение могло потеряться уже после записи. Поэтому при `503` повторяйте тот же UUID и тело.

## 9. Разобрать результаты с помощью SQL

Число уникальных событий по инцидентам:

```sql
SELECT incident_id, count(*) AS events
FROM kafka_lab.processed_events
GROUP BY incident_id
ORDER BY events DESC, incident_id;
```

Уникальные результаты и повторно опубликованные события:

```sql
SELECT count(*) AS kafka_positions,
       count(*) FILTER (WHERE duplicate) AS duplicate_positions,
       count(DISTINCT event_id) AS unique_events
FROM kafka_lab.deliveries;
```

Распределение успешно обработанных позиций по разделам:

```sql
SELECT partition, count(*) AS deliveries, min(offset_value) AS first_offset,
       max(offset_value) AS last_offset
FROM kafka_lab.deliveries
GROUP BY partition
ORDER BY partition;
```

Объясните, почему разность максимального и минимального смещений может отличаться от количества строк. В частности, ошибочные сообщения уходят в DLQ и не создают строки успешной доставки в БД.

## 10. Сохранность после штатного перезапуска

Запишите количество результатов и UUID одного события. Остановите обработчик через **Ctrl+C**, затем выполните:

```powershell
.\scripts\kafka\Broker.ps1 -Action Stop
.\scripts\lab\Stop-Lab.ps1
.\scripts\lab\Start-Lab.ps1
.\scripts\kafka\Broker.ps1 -Action Start
```

Запустите обработчик во втором терминале. Проверьте сохранённый результат и отправьте новое событие.

**Ожидается:** прежние результаты сохранены, новое событие обрабатывается. Штатная остановка проверяет сохранность при обычном перезапуске; поведение при аварийном завершении между SQL-фиксацией и фиксацией смещения требует отдельного управляемого опыта. Не выдавайте этот шаг за доказательство доставки «ровно один раз».

Заполните краткий итог занятия: какие ответы API увидели, сколько уникальных событий и повторов получили, что оказалось в DLQ, как изменялось отставание группы.
